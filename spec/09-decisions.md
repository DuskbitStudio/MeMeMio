## §9.1 库是共享的 · 2026-09-13 · accepted

**决定：所有人的上传进同一个库，所有登录用户都能搜到全部内容。编辑描述与标签对全员开放，删除和重新打标限上传者本人或管理员。**

这一条编号为 1，因为它不是并列的一项取舍，而是下面所有取舍的前提——[§9.3](#93-视觉模型用户可配embedding-归部署方--2026-09-13--accepted) 和 [§9.6](#96-embedding-必须全站统一共享库的最大技术约束--2026-09-13--accepted) 的形态完全由它决定。

| 维度 | 归属 |
|---|---|
| 图片内容、描述、标签 | 共享，全员可搜可用 |
| 编辑描述与标签 | 全员可改 |
| 删除、重新打标 | 上传者本人或管理员 |
| 收藏 | 每人独立 |
| 视觉模型配置 | 每人独立 |
| Embedding 模型配置 | 全站一份，仅管理员 |

**为什么共享：** 表情包的价值随库的规模增长，而好图是稀缺的——同一个圈子里，别人收藏的那张正好是你想要的，概率相当高。每人一个隔离库等于把 N 个人的贡献切成 N 份，每份都很小，而这个项目的整个前提就是「库大到自己找不着了」。

**为什么编辑不设限、删除设限：** 标签在共享库里是**公共品**——谁发现标错了都顺手改掉，对所有人都是净收益，拦住反而降低质量。删除是不可逆的破坏性操作，两者的风险不对称，所以待遇不同。记一个 `edited_by` 防滥用就够了。

**换来的代价有三个，都必须正视：**

1. **Embedding 模型不能再各用各的**——硬性技术后果，见 [§9.6](#96-embedding-必须全站统一共享库的最大技术约束--2026-09-13--accepted)
2. **打标质量从私事变成公共品**——一个人配了烂模型，污染的是所有人的搜索结果，见 [§9.3](#93-视觉模型用户可配embedding-归部署方--2026-09-13--accepted)
3. **私密性消失**——[§9.5](#95-敏感内容双通道降级不是二选一--2026-09-13--proposed) 说个人库里必然有擦边内容，那些内容现在默认对所有被邀请的人可见。这不是代码问题，是邀请谁之前要先想清楚的事

实施要求（风险从读路径整个挪到了写路径）见 [§3.4](03-auth-permission.md)。

## §9.2 形态：Web SPA，以及「发送」这一步的真实能力边界 · 2026-09-13 · accepted

**决定：** 标准单页应用（Vite + React），前后端同域部署，不用 Next.js。

**取舍：** 桌面端（Tauri/Electron）在「发送」这一步明显更强——能把**文件**放进系统剪贴板，GIF 可以直接 Ctrl+V 发进微信；还能读本地缓存目录、做全局快捷键唤起。Web 端做不到这些。

选 Web 的理由：部署一次所有人可用、跨设备、手机端天然支持。而手机端恰恰能绕开 Web 最大的短板。

**它不是 Next.js 的理由：** 这东西是登录后才能用的工具，没有 SEO 需求、没有首屏压力、不需要 SSR。Next.js 在这里只增加心智负担。SPA + 独立 API 更合身。

### 能力边界

这是整个产品的价值所在，也是 Web 形态最大的约束，必须说清楚。

浏览器的 `ClipboardItem` 规范只保证 `text/plain`、`text/html`、`image/png` 三种类型。这意味着：

| 场景 | 能力 | 体验 |
|---|---|---|
| 桌面 · 静态图（PNG/JPG/WebP） | 写入剪贴板 | ✅ 点击即复制，切回微信 Ctrl+V |
| 桌面 · 动图（GIF/APNG） | **写不进剪贴板** | ⚠️ 退化为下载后拖入，或从网页直接拖进聊天窗口 |
| 手机 · 任意格式 | `navigator.share({files})` | ✅ 直接分享到微信，动图也可以 |

**手机端反而是体验最好的一端。** 这也是选 Web 形态的重要依据。

UI 上必须诚实区分这两类，不能让用户点了 GIF 之后发现没反应。因此每条记录要存 `is_animated` 字段，前端据此决定走哪条路径，见 [§5.2.2](05-data-models.md)。

拖拽到微信窗口的可行性尚未验证，见 [§9.12](#912-起待验证项--2026-09-13--proposed)。

## §9.3 视觉模型用户可配，Embedding 归部署方 · 2026-09-13 · accepted

**决定：** 视觉模型由用户在设置页自行填写；Embedding 模型全站一份，仅管理员可改。两者都只要求接口兼容 OpenAI 规范。

**为什么两者待遇不同：** 视觉模型的产出是**文本**（描述、标签、OCR），跨模型天然可比，只要固定标签词表执行到位（见 [§4](04-vocabulary.md)）。Embedding 的产出是**向量**，跨模型完全不可比——而库是共享的，A 的查询要和 B 上传的图放在一起比。完整论证见 [§9.6](#96-embedding-必须全站统一共享库的最大技术约束--2026-09-13--accepted)。

| 配置组 | 字段 | 谁来配 |
|---|---|---|
| 视觉打标 · 主通道 | Base URL / API Key / Model | 用户（不填则用部署方默认） |
| 视觉打标 · 副通道（降级用，可留空） | Base URL / API Key / Model | 用户 |
| 向量 Embedding | Base URL / API Key / Model | **仅管理员，全站一份** |

接口约定固定为 OpenAI 兼容的 `/v1/chat/completions` 和 `/v1/embeddings`——这是事实标准，几乎所有供应商和中转服务都支持。

**视觉模型默认就用部署方的配置，用户设置页里这一组收进「高级选项」。** 旁边必须写明一句：你的打标结果会进入公共库。这是共享带来的新问题——原来配了烂模型只有自己搜不准，现在会污染所有人的搜索结果，而打标质量恰恰是这个项目的命门。因此还需要给管理员一个「对任意图片重新打标」的兜底入口，见 [§6.4](06-endpoints.md)。

> ⚠️ **那条兜底入口只落了一半（2026-09-22 更正）。** `POST /memes/retag` 已实现，但它**按每张图自己上传者的配置**跑——后台队列里没有请求上下文，拿不到「谁点的按钮」。所以管理员**重置不了别人的配置**：图的上传者自己配了差模型，重打还是用那个差模型；上传者压根没配通道，那张图连重打都排不进去。要真做到本段设想的那样，得给 `tag_jobs` 加一列存配置快照并串到配置解析。**在那之前，「用差模型污染公共库」这件事仍然只能靠人工 `PATCH` 逐张收拾。** 见 [§6.4.3](06-endpoints.md)、[§9.25](#925-重打标跳过人工编辑过的图2026-09-22--accepted)。

**成本模型基本不变。** 贵的是视觉打标，仍由上传者自己的 key 承担；Embedding 转由部署方承担，但那部分本来就可以忽略——入库时每条一次、搜索时每次一次，量级在单张图打标成本的百分之一以下。原本为了保护 AI 预算而设的「每用户图片数配额」，仍然只需要限制存储容量即可，见 [§3.6](03-auth-permission.md)。

**代价要认：** 接口抽象只能用最小公分母。各家的 Batch 折扣、`json_schema` 严格结构化输出、显式 prompt caching 用法都不一致，抽象层里都用不上。结构化输出退化为 `json_object` + 提示词里写明 schema + 健壮的解析兜底。

**为什么这笔交易划算：** 牺牲掉的特性主要用来省钱，而单张图的打标成本本就在 $0.001 以下的量级，省钱不是优先级。换供应商的自由度价值更高——尤其在 [§9.5](#95-敏感内容双通道降级不是二选一--2026-09-13--proposed) 的内容问题上，这层抽象直接变成了解决方案。

**安全要求：** API Key（不论用户的还是部署方的）必须加密存储（AES-GCM，主密钥放环境变量），前端只回显后四位，任何接口都不得返回完整 key。见 [§3.5](03-auth-permission.md)。

## §9.4 动图处理：抽帧，而不是指望模型看懂动图 · 2026-09-13 · accepted

**问题不是格式支持，是模型只看得到一帧，而那一帧往往是错的。** 表情包动图的第一帧通常是铺垫——人物还没做表情，**文字往往要到后面几帧才出现**。用首帧打标等于丢掉全部关键信息。

**决定：** 动图永远不直接送给 AI，服务端统一归一化。

```
上传文件
  → magic bytes 探测真实格式（不信扩展名）
  ├─ 动图 → ffmpeg 抽全帧 → pHash 去重（去掉长静止段的重复帧）
  │         → 去重后 ≤ 10 帧则全发；> 10 帧才采样，偏向后段
  │         → 各自缩放为独立 PNG，一次请求最多发 10 张
  └─ 静图 → 长边缩到 512 的 PNG
  → AI 只会收到 PNG
```

**为什么上限是 10：** 上限存在只是为了给成本和请求大小封顶，不是为了省帧。取 10 而不是 4，是因为 4 会裁掉绝大多数动图。

**实测数据**（2026-09-13，取自一个 989 张的真实 QQ 收藏库，252 个 GIF 中随机抽 40 个，逐帧感知哈希去重）：

| 指标 | 值 |
|---|---|
| 原始帧数 中位数 / 均值 / 最大 | 30 / 42 / 243 |
| **去重后**不同状态数 中位数 / 均值 / 最大 | **9 / 15.3 / 81** |
| 去重后 ≤ 10 帧的比例 | **55%** |
| 去重后 ≤ 4 帧的比例 | **28%** |
| 单帧 GIF（伪动图） | 252 个里有 13 个 |

结论有两条，方向相反：

- **上限 10 是合理的**——它让一半以上的动图完全不需要采样。如果取 4，**72% 的动图都会被裁**，而被裁掉的正是帧数多、内容变化多的那些
- **但「10 对多数动图等于不裁剪」只对一半成立**，长尾比预期厚得多（均值 15.3，最大 81）。分镜式、多段文字的长动图是真实存在的常见形态，不是边角情况

> 上表的去重阈值是估算用的近似哈希，和实现里最终采用的 pHash + 阈值不同，数字会变。**方向可信，绝对值不可直接引用。** 正式测量属于[评测集](../joint-tasks/2026-09-13-eval-set.md)。

这个值**是可调的，但不是随便调的**。往下调会先伤到文字中途变化的动图（OCR 覆盖不全），往上调会先撞供应商的单请求图片数上限。它的验证依据是[评测集](../docs/eval.md)里动图那一类的 OCR 包含率，见 [§9.16](#912-起待验证项--2026-09-13--proposed)。

> ⚠️ **图片数超限是运行时才暴露的失败。** `vision_multi_image` 是布尔值，只说明"支不支持多图"，**不说明"最多几张"**，测试连接探测不出上限。因此供应商返回图片数超限类错误时，必须降到 4 帧重试，仍失败再回退拼图——**不能让它变成打标失败**。降级顺序见 [§2.4](02-errors.md)。

**为什么是发多张而不是拼成 2×2 网格：** 多数模型对单图有 token 上限（如 DeepSeek 的 384 tokens），拼四格等于每帧只剩四分之一的分辨率预算，表情包里的小字会糊掉。发独立帧能让每帧都吃满分辨率，总成本仍可忽略。拼图方案作为兼容性兜底保留——供应商如果不支持多图输入，自动回退到拼图。是否支持多图由测试连接实测，见 [§9.7](#97-系统不替用户猜能力靠实测近似重复靠人判断--2026-09-13--accepted)。

**兜底拼图仍然是 2×2 的 4 帧，不随上限一起涨。** 拼图受限于分辨率而不是数量，3×3 只会让小字更糊。两条路径的帧数不同是有意的。

**这个设计在「模型用户可配」之后变得更重要。** 用户会填各种各样的模型，格式支持千差万别（DeepSeek 支持 JPEG/PNG/GIF/WebP，Grok 只支持 jpg/png）。但既然所有模型都只会收到 PNG，**格式兼容性问题被彻底消除**——用户不需要关心自己选的模型支不支持 GIF。

原图原样存 R2，展示和发送始终用原图，只有喂 AI 这一路做归一化。

## §9.5 敏感内容：双通道降级，不是二选一 · 2026-09-13 · proposed

个人表情包库里必然存在擦边内容。境内受监管的模型对这类内容大概率在 API 层就拦截——**这是合规问题，不是能力问题，调提示词绕不过去**。

**决定：** 利用 [§9.3](#93-视觉模型用户可配embedding-归部署方--2026-09-13--accepted) 的双通道配置做失败降级，而不是前置分类器。主通道和副通道**都由用户自己填**，用户可以自行决定副通道用哪家。

```
主通道（用户配置）跑全部
  ↓ 被拒（HTTP 内容策略错误 / 返回非合法 JSON / 文本含拒绝措辞）
副通道（用户配置，可留空）自动重试
  ↓ 仍失败或未配置副通道
标记 tag_status = needs_manual，进待人工处理列表
```

**为什么用「拒绝后降级」而不是「前置 NSFW 分类器」：** 少一个模型、少一次推理，而且能顺带覆盖没预料到的拒绝类型（血腥、某些政治梗图一样会被拒）。

**即使两边都失败也不是全丢：** 缩略图和已有的 OCR 文字仍在，那张图依然能被文字搜到，只是没有语义描述。降级是分级的，不是二值的。见 [§2.4](02-errors.md)。

**配套约束：** 两个通道输出的标签词汇必须对齐（一个说「无语」一个说「speechless」的话标签检索就废了）。因此**固定标签词表从「好习惯」变成硬性要求**——提示词里给死一份中文标签清单，模型只能从里面挑。用户可配置模型之后这一条更关键，因为系统完全无法预知用户会填什么模型。见 [§4.1](04-vocabulary.md)。

**边界：** 涉及未成年人的内容在所有供应商和法律层面都是硬禁的，不存在「换一家就能过」，这类应在入库前拦截。

**共享库让这个边界的分量变重了。** 原本擦边内容只有上传者自己看得到，现在**默认对所有被邀请的人可见**（见 [§9.1](#91-库是共享的--2026-09-13--accepted)）。托管责任仍在部署方，但多了一层：你邀请的人会看到彼此传的所有东西。开放邀请前必须先想清楚这件事，它不是技术问题。

**状态为 `proposed` 的原因：** 拒绝的具体形态（HTTP 错误码？200 但正文是拒绝措辞？JSON 结构完整但字段为空？）尚未实测，而降级逻辑的检测方式完全取决于这个结果。见 [供应商探测任务](../joint-tasks/2026-09-13-provider-spikes.md)。

## §9.6 Embedding 必须全站统一：共享库的最大技术约束 · 2026-09-13 · accepted

**这是 [§9.1](#91-库是共享的--2026-09-13--accepted)「库共享」带来的最大技术后果，必须单独讲。**

如果库是隔离的，不同用户用不同 embedding 模型完全没问题——每个人只在自己的库里检索，跨用户的向量从不放在一起比较，「向量空间不兼容」根本不构成问题。

**但库是共享的，这个前提不成立了。** 用户 A 输入查询 → 用 A 的模型编码 → 和**全库**的向量做余弦比较，其中包括 B 用另一个模型编码的那些。不同模型的向量空间之间没有任何对应关系，1024 个维度各自代表什么完全不同。结果不是「差一点」，是**噪声**——B 上传的图要么永远搜不到，要么随机冒出来。

**所以 Embedding 模型全站一份，由管理员配置，普通用户看不到这一组。** 真正的硬要求是「同一个模型、同一个版本」，维度一致只是顺带满足。

> **措辞更正（2026-09-24）。** 这句原来写的是「普通用户的设置页里**没有**这一组」。实质约束一个字没变（全站一份、仅管理员可改、换模型触发全站重算、维度归一化到 1024），变的是它挂在哪个 URL 下：三个管理页并进 `/settings` 之后（[任务](../_archive/joint-tasks/2026-09-18-settings-merge.md)），它仍**不渲染给普通用户**，但和视觉模型同处一个页面。**「哪些人看得见」是契约，「在哪个 URL」不是**——所以这次改的只是描述，不是决定。

> 「每张图存 N 份向量、每个模型一份」这个方案不用考虑：新用户填个新模型就要全库重嵌一遍，成本和复杂度都不成立。

**维度仍然固定 1024**，任何模型的输出都归一化到 1024：

| 模型原生维度 | 处理 |
|---|---|
| > 1024 | 取前 1024 维 + **重新做 L2 归一化** |
| = 1024 | 直接使用 |
| < 1024 | **拒绝保存配置**，管理页标红提示 |

归一化这步很容易漏，漏了余弦相似度就不对了。

**为什么截断可行：** 支持 MRL（套娃表征）的模型——Qwen3-Embedding 全系、OpenAI text-embedding-3 全系等——截断基本无损，这是训练时就设计好的能力。不支持 MRL 的模型截断会明显掉质量，所以管理页必须明确提示优先选 MRL 模型。

优先走 OpenAI 的 `dimensions` 参数让服务端直接返回 1024 维；**若供应商不透传该参数，则客户端截断 + 重新归一化**。两条路由「测试连接」自动探测决定。

**换 Embedding 模型 = 全站重算。** 但这件事的性质变了——从「每个用户随时可能触发」变成「管理员偶尔做一次的运维操作」，频率低得多，UI 复杂度也随之下降：

- 管理页一个「重建索引」按钮 + 进度，不需要面向普通用户的确认弹窗
- 每条记录存 `embed_model`，用于判断哪些记录已过期
- 重算期间搜索自动降级为只用 OCR + 标签，不中断服务（响应里 `degraded: true`，见 [§6.3.1](06-endpoints.md)）

代价不大：几千条重算只要几分钟、几毛钱。

**一个附带的技术红利。** 原方案的向量检索是 `HNSW + WHERE user_id = ?`，这是 pgvector 的经典痛点——带过滤条件的近似搜索会掉召回率，要靠调 `ef_search` 或 iterative scan 补回来。库共享之后这个过滤条件消失了，HNSW 跑在它最舒服的状态。（软删的 `deleted_at is null` 是个轻量过滤，选择率接近 1，不构成同类问题。）

## §9.7 系统不替用户猜：能力靠实测，近似重复靠人判断 · 2026-09-13 · accepted

> **2026-09-29：「近似重复靠人判断」这一半被 [§9.33](#933-近似重复距离-0-直接判重其余交给打标通道的视觉模型模型拿不准才进待确认队列--2026-09-29--accepted) 部分取代（`accepted`，两端已实现，真链路验收未做）**——距离 0 直接判重、1–8 先问视觉模型、模型拿不准才进队列。「能力靠实测」那一半不变。

两件看起来不相干的事，背后是同一条原则：**系统不知道的事，不要假装知道。**

### 模型能力靠实测，不靠声明

用户会填各种中转服务，实际行为经常与文档不符。**不让用户手填维度、也不假设任何能力，全部实测。**

「测试连接」点击后执行：

**视觉模型检测**（用户设置页）

1. 发送一张内置测试图 + 正式的打标提示词
2. 检查：能否接收图片 / 返回是否为合法 JSON / 标签是否落在固定词表内
3. 探测是否支持 `response_format: {"type":"json_object"}`，不支持则自动回退到纯提示词模式
4. 探测是否支持多图输入，不支持则动图自动回退到拼图模式（见 [§9.4](#94-动图处理抽帧而不是指望模型看懂动图--2026-09-13--accepted)）
5. **失败时把模型的原始返回原样展示出来**，让用户能判断是模型能力问题还是配置填错

**Embedding 检测**（管理页）

1. 发送一段测试文本
2. **自动探测实际输出维度**——以实测为准，不信文档、不让人手填
3. 探测 `dimensions` 参数是否生效，决定服务端降维还是客户端截断
4. 维度 < 1024 直接标红并**拒绝保存**
5. 若库里已有数据且模型与当前不同，保存前额外确认一次——这会触发全站重建索引

**测试不通过不允许保存配置。** 这一条能挡掉绝大部分「配好了但跑不起来」的情况，是整个可配置设计能不能落地的关键。

因此 `user_ai_configs` / `embed_config` 里的探测结果字段**不接受客户端写入**——它们只能由测试连接接口写入。用户手填的「支持多图」不算数。接口形态见 [§6.5](06-endpoints.md)。

### 近似重复交给人判断，DB 不先斩后奏

两层去重，性质完全不同：

| 层 | 手段 | 判断权 |
|---|---|---|
| 精确重复 | SHA-256，**全局唯一约束** | 机器，零误判，静默跳过 |
| 近似重复 | pHash + Hamming 距离，**只建普通索引** | **人** |

**pHash 刻意不做唯一约束。** 它会误判——同一模板换了字的两张表情包 Hamming 距离可能很近，但它们是两张不同的图，都该留下。如果把它设成唯一约束，第二张图会在写入时直接失败，用户连「让我自己看一眼」的机会都没有。

所以近似命中走**待确认队列**：把两张图并排摆出来，让用户自己判断是重复还是不同。见 [§6.2.3](06-endpoints.md)。

**为什么是队列而不是中途弹窗：** 上千张图导入时每张都弹窗体验会崩掉。近似命中不阻塞导入，攒起来导入结束后一起处理。队列里只有 1 条时前端把它呈现成即时弹窗即可——**同一个接口，不同的呈现形式**，不为单张上传另做一套。

**代价：** 待确认的图在用户处理之前不打标、搜不到。这是为了不给被判为重复的图白花 AI 的钱；如果实际使用中发现待确认队列经常积压，这一条可以改成「先打标，用户拒绝后再删」，反向的取舍是多花一点钱换即时可搜。

### 视觉打标推荐：DeepSeek V4.1 Flash

（2026-09-10 发布，原生多模态，OpenAI 兼容）

**推荐理由不是价格，是中文语感。** 「阴阳怪气」「摆烂」「表面同意实际很无语」这类判断是整个产品的命门，国产模型在这上面大概率优于英文模型。

成本参考（官方定价，供用户估算自己的开销）：

|---|---|

| 输入（缓存命中） | $0.006 / MTok |
| 输出 | $1.20 / MTok |
| 单张图片 | ≤ 384 tokens |

单张约 **$0.0007**，1000 张不到 1 美元，闲时再减半。

该模型的 prompt caching 是服务端按前缀自动命中的，不需要手动标记——把固定提示词和标签词表放在消息最前面，这部分几乎免费。这是少数没有被兼容层牺牲掉的省钱特性。

### Embedding 推荐：Qwen3-Embedding-4B（硅基流动托管）

Embedding 归部署方统一配置（见 [§9.6](#96-embedding-必须全站统一共享库的最大技术约束--2026-09-13--accepted)），所以这是一个**全站做一次、影响所有人**的选择，比原来更需要有依据。Qwen3-Embedding 三档的原生维度是 0.6B=1024、4B=2560、8B=4096。

**为什么不是 8B：** 不是质量，是**搜索延迟**。每次搜索都要实时跑一次查询 embedding，8B 明显更慢，叠加 HyDE 的那次 LLM 调用会让搜索体感变差。导入时慢无所谓（异步），搜索时慢直接伤体验。4B 到 8B 的质量差距很小，这笔交易划算。

**为什么不是 0.6B：** 本项目语料只有几千条短描述，召回根本不难，难的是「可爱一点的滚」这种细微语义的区分度——这吃模型容量，不吃向量维度。0.6B 到 4B 是明显的一档差距。

**一个必须避免的误解：模型容量和输出维度是两个独立的旋钮。** 不要为了凑 1024 维去选 0.6B——4B 和 8B 通过 MRL 一样能输出 1024 维。

**instruct 是非对称的。** Qwen3-Embedding 是 instruction-aware 模型，正确用法是查询侧加前缀、文档侧不加：

```
查询侧：Instruct: {任务描述}\nQuery: 今天真的不想上班
文档侧：一只趴在桌上的猫，看起来非常疲惫……（原文，无前缀）
```

两边都加或都不加会损失几个点。注意这条只对 instruction-aware 模型成立，换成别的模型就不适用——因此这个行为应当**跟随 Embedding 配置，而不是写死在代码里**。

**状态为 `proposed` 的原因：** 这些推荐值来自公开信息和通用榜单，尚未在本项目的评测集上验证。通用榜单不代表「中文梗图语义」这个具体任务。见 [评测集任务](../joint-tasks/2026-09-13-eval-set.md)。

## §9.10 检索：三路混合 + RRF 融合 · 2026-09-13 · accepted

单一检索方式都有明确的失效场景，所以必须混合：

| 通路 | 擅长 | 失效场景 |
|---|---|---|
| OCR 全文 | 「你没事吧」这种精确记得图上文字的 | 无文字表情包 |
| 标签过滤 | 「猫 + 无语」这种结构化筛选 | 说不出标签的模糊意图 |
| 语义向量 | 「今天真的不想上班」这种描述意图的 | 精确文字匹配反而不如全文 |

**融合用 RRF（倒数排名融合），不用加权求和。** 向量相似度和全文检索分数量纲完全不同，加权的权重根本调不出来；RRF 只用排名不用分数，天然免疫这个问题。

**Embedding 统一之后这条论证弱化了但没消失**——同一时刻全站用同一个模型，分数分布至少是一致的；但管理员换一次模型，相似度的绝对值分布就整体漂移一次，写死的加权阈值又得重调一轮。RRF 只看排名，换模型不受影响。

**查询侧改写（HyDE）：** 用户输入「今天真的不想上班」是一句短口语，而库里存的是「一只趴在桌上的猫，看起来非常疲惫……」这样的长描述。短句对长文的向量匹配效果一般。先用小模型把查询改写成一句同样风格的描述再检索，成本极低、收益明显。改写复用**搜索者本人**配置的视觉模型通道（纯文本调用）——改写产出是文本，再交给全站统一的 Embedding 编码，所以不存在跨模型不兼容的问题。

**中文全文检索的坑。** PostgreSQL 默认的 `to_tsvector` 不会分中文词，直接用等于没用。两个选择：装 `zhparser`/`pg_jieba` 扩展做真正的分词，或者用 `pg_trgm` 做子串匹配。**MVP 选后者**——OCR 精确搜索的本质就是子串匹配，`pg_trgm` 够用，而且不用在部署环境里折腾扩展。

**Reranker 不开放给用户配置。** Qwen3-Reranker 精排是打标质量之外提升最大的杠杆，但它归管理员：reranker 虽然是查询时作用于搜索者自己的结果列表、技术上允许各用各的，但那样每个人搜到的排序都不一样，评测集也没法用，得不偿失。首期不做，见 `docs/product.md` 的后续扩展。

具体参数（RRF 的 k、各通路召回条数、HyDE 提示词）是实现约束，见 `api/agents/rules/retrieval.md`。

## §9.11 不引入 Redis：队列和会话都用 PostgreSQL · 2026-09-13 · accepted

**决定：** 打标任务队列用 `FOR UPDATE SKIP LOCKED` 在 PostgreSQL 里实现，会话也存 PostgreSQL。整套系统只有一个有状态组件。

**取舍：** Redis 做队列更顺手，BullMQ 这类库开箱即用，重试、延迟、优先级都不用自己写。放弃它意味着这些要自己实现一部分。

**为什么值得：** 本项目的负载特征非常明确——任务量是**几千条量级**，不是几百万；并发消费者是**个位数**，不是几十台 worker。在这个量级上 PostgreSQL 的 `SKIP LOCKED` 完全够用，而少一个组件意味着：

- 部署只有 app + db 两个容器，不需要额外的持久化和备份策略
- 任务状态和业务数据在同一个事务里，「图片入库了但队列任务丢了」这类不一致根本不会发生
- 备份一个数据库就是备份全部状态

**什么情况下该推翻这条：** 如果导入量级涨到十万条以上，或者出现了需要延迟队列 / 优先级队列的场景，`SKIP LOCKED` 的手写实现会开始变复杂。到那时再引入 Redis 是合理的——但那是一次有明确触发条件的迁移，不是现在该预留的复杂度。

## §9.18 梗名不进闭集词表，走别名层 · 2026-09-13 · proposed

**问题不是模型认不出，是模型叫不出名字。**

用户搜的是「奶龙」「哈基米」「耄耋」，不是「黄色的小龙」「橘猫」「猫」。视觉模型在描述层面表现稳定——「一只黄色的小龙，圆脸，张嘴」几乎不会错；但在命名层面不可靠，因为梗是社群知识，长尾、高速更新、且大量晚于训练截止。

**逼模型命名比不命名更糟。** 它不会说「不认识」，它会自信地给一个相近的错名字。共享库里一个错的梗名会被所有人搜到、被后来的人当成事实。**空标签只是搜不到，错标签是污染**——见评测集的「标签污染率」指标。

`耄耋` 是最能说明问题的例子：它是真实存在的词，字典义是「老年人」，在梗里指猫。**再强的视觉模型看到一只猫也不会说出「耄耋」，而 embedding 反而会把这个查询匹配到老年人的图上。** 这是词汇映射问题，不是感知问题，优化识别永远解决不了。

**决定：分成两件事处理。**

| | 谁负责 |
|---|---|
| 看出来是什么（颜色、物种、形态） | 视觉模型，进 `description` |
| 它叫什么梗名 | **不问模型**，走下面三扇门 |

### 梗名进入系统的三扇门

1. **OCR** —— 大量梗图自带梗名或台词。已有路径，零成本
2. **人工补标** —— 第一个认识的人标一次，全站永久受益。这是[开放编辑](#91-库是共享的--2026-09-13--accepted)最大的红利：梗是社群知识，本来就该由知道的人补上，而不是指望模型
3. **原始文件名** —— 从网上保存的表情包文件名里常带梗名。因此 `original_filename` 入库并参与 `pg_trgm`，但**不进 embedding**，见 [§5.2.3](05-data-models.md)

共享库在这件事上从「代价」变成了「资产」。一千张图里通常只有几十个梗族，补标是一次性且收敛的工作量。

### 别名层

梗名**绝不能进 [§4](04-vocabulary.md) 的固定词表**：

| | 固定词表 | 梗名 |
|---|---|---|
| 性质 | **闭集** | **开集** |
| 存在理由 | 让不同模型的输出可比 | 记录社群实际在用的叫法 |
| 变更成本 | 按不兼容处理，影响已有数据（[§4.4](04-vocabulary.md)） | 加一条就是加一条 |

把一个每月都在长的集合塞进闭集，会毁掉闭集的全部意义。

别名层的作用是**查询期的确定性扩展**：

```
用户搜「哈基米」
  → 查别名表命中 → 扩展为「哈基米 OR 橘猫 OR 黄色的猫」
  → 三路检索照常
```

> ⚠️ **必须是查表，且必须放在 HyDE 之前。**
>
> HyDE 用的是用户配的模型，那个模型同样不认识哈基米——指望它改写等于把问题原样推给下一层。别名扩展是确定性的、可解释的、可被用户修正的；HyDE 不是。

### 冷启动来源

**记录零结果搜索。** 用户搜了什么、没搜到——那是一份真实的、本站用户实际在用的梗名清单，比任何人拍脑袋列的都准。别名表的初始内容从这里来。

### 明确不做

- **微调模型** —— 直接与[模型用户可配](#93-视觉模型用户可配embedding-归部署方--2026-09-13--accepted)冲突，且梗的更新速度快于任何微调周期
- **在打标提示词里塞梗名清单让模型对号入座** —— 清单一长模型就开始硬套，污染率会飙
- **参考图 few-shot** —— 成本随梗数线性增长，不收敛

打标提示词唯一要改的是一句约束：**具体描述外观，不确定时不要猜 IP 名**。这样 `description` 才能成为稳定的连接键。

### 为什么是 `proposed`

别名表的**存储位置与数据形态尚未定**（进 `tags[]` 的开放命名空间，还是独立表），扩展的召回代价也没测过。落地方案见[梗名别名层任务](../joint-tasks/2026-09-13-meme-lexicon.md)。

本条的**原则部分**（梗名不进闭集、不让模型命名、文件名入库）可以直接依赖，不必等任务完成。

## §9.19 人工编辑不触发向量重算 · 2026-09-19 · accepted

**决定：`PATCH /memes/{id}` 改完 `description` 与三个标签数组后，不重算 embedding，也不把这条排进重算队列。`search_text` 照常在写入时重算（[§5.2.3](05-data-models.md)），向量保持陈旧。**

**为什么不做：** 改 `search_text` 就等于让 `embedding` 过期，看起来「顺手重算一下」是显然的收尾——但对这个项目不是。

[§9.1](#91-库是共享的--2026-09-13--accepted) 把编辑开放给了所有人，[§9.3](#93-视觉模型用户可配embedding-归部署方--2026-09-13--accepted) 又把 embedding 的账记在部署方头上。两条放在一起，**「编辑一次重算一次」就是一条任何人都能走的烧钱路径**：不需要恶意，一个人把库里的图挨个点进编辑面板改个错别字，就是全库重算。而这条路径换来的收益很小——被改的字段本来就落在 `pg_trgm` 与标签过滤两路上，向量陈旧只让那一张图在语义检索里排得偏后，不会让它搜不到。

**换来的代价，必须记清楚：**

- 被编辑过的图，语义检索质量下降（三路少一路准确）
- **`GET /admin/reindex/status` 的 `stale` 看不见它。** 那个数的口径是 `embed_model` 与当前模型不一致，而人工编辑不改 `embed_model`。所以会出现「`stale: 0` 但搜出来的东西不太对」，**这不是 bug**，是本节写下的取舍
- 补的办法是管理员手动 [`POST /admin/reindex`](06-endpoints.md#654-重建索引)——它按 `search_text` 重算，正好覆盖这一类

**这是一条可推翻的决定，不是原则。** 触发重新考虑的条件：向量陈旧的实际影响被证明比预估大（比如被编辑的图在语义检索里明显沉底），或增量重算有了便宜到可以随编辑走的实现（单条、异步、有预算上限）。届时的落点是「编辑后入队一条重算任务」，而不是「编辑时同步重算」——同步会把一次普通编辑的延迟绑在部署方的 embedding 供应商上。

见[浏览页图片操作](../_archive/joint-tasks/2026-09-19-browse-meme-actions.md)。

## §9.20 换 embedding 模型期间，向量路过滤而不是停摆 · 2026-09-22 · accepted

**决定：向量通路的召回条件加上 `embed_model = 当前配置的模型`。库里还有旧模型算的向量时，向量路照常跑、只在当前模型那一部分里跑，同时把 `degraded` 置为 `true`。**

**在此之前是两句互相矛盾的话。** [§6.3.1](06-endpoints.md#631-搜索) 写着重建索引期间「没有走向量通路」，而实现是向量路照常全量跑、只把 `degraded` 标上——理由写在代码注释里：「旧向量也是向量，能召回总比召不回强」。

**那句注释是错的。** 两个模型的向量不在同一个空间里，它们之间的余弦相似度不是「更像」，只是噪声。混进 RRF 之后，旧向量不是「弱一点的结果」，而是**随机排名的结果被当成有意义的排名**——它挤掉的是另外两路的真结果。「能召回总比召不回强」成立的前提是召回的东西和查询有关，这里不成立。

**但整条路停摆也不对：** 重算是逐条推进的，已经算完的那部分向量是完全好的。全库停摆意味着重算跑到 99% 时向量路仍然是关的。

所以取中间：**按模型过滤**。代价是重算期间召回覆盖不全，这一点由 `degraded` 如实报告，不假装无事发生。

**顺带修掉一个静默失效。** `degraded` 原先只看有没有 `pending` / `running` 的重算任务。重算任务耗尽重试后落在 `failed` 并留在表里，于是「未完成任务」变成 0，而那些记录的向量仍然是旧模型的——过滤前是**永久静默的混模型**，过滤后是**永久 `degraded: true`**。后者管理员看得见，前者看不见。判定口径因此改成 `pending` / `running` / `failed` 三者之一存在即降级。

**代价记清楚：**

- HNSW 上加了一个等值过滤。稳态下 `embed_model` 的选择率≈1（全库都是当前模型），对索引扫描几乎无影响；只有换模型期间选择率才下降，而那正是我们要它生效的时候。这与 `deleted_at is null` 是同一类过滤，见 `api/agents/rules/database.md`。
- 换模型期间 `degraded` 会一直是 `true`，直到最后一条重算完。这不是噪声，是事实。
- 重算任务卡在 `failed` 时 `degraded` 不会自己好。这是有意的：它是一个需要人处理的状态，不该被自动抹平。

**什么情况下该推翻：** 如果出现「同一模型不同版本向量仍然可比」的场景（例如只是升了小版本），按模型名严格相等会把可用的向量也挡掉。届时的落点是给 `embed_config` 加一个显式的「兼容组」标识，而不是放松这里的比较。

## §9.21 文本通路不匹配标签，标签只由标签通路命中 · 2026-09-22 · accepted

**决定：`pg_trgm` 匹配 `ocr_text` + `description` + `original_filename`，不再匹配 `search_text`。`search_text` 保留原定义（含七个数组），但它只喂 embedding。**

**问题：同一个词被算两次分。** `search_text` 里拼进了标签值，而标签通路又精确匹配同样的标签。搜「无语」时，一张标了 `无语` 的图会同时出现在文本路和标签路里，RRF 给它两份分；而一张图上真写着「无语」但没标这个标签的图只有一份。

**这不是「多路验证，加分合理」。** RRF 的前提是各通路**独立**地对相关性投票（[§9.10](#910-检索三路混合--rrf-融合--2026-09-13--accepted)）。两条通路读的是同一个字段时，它们不是两个证据，是一个证据被数了两遍。数出来的结果是：标签沾边的图能压过原文精确命中的图——而「精确记得图上那句话」正是文本通路存在的唯一理由。

算一下就清楚：标签路排第 1（`1/61 ≈ 0.0164`）对上文本路排第 50 + 标签路排第 50（`2 × 1/110 ≈ 0.0182`）。后者赢。这不是参数没调好，是同一个信号被计了两次。

**代价：** 没有任何标签命中、只靠标签词出现在 `search_text` 里被 trgm 捞回来的那类结果消失了。它们本来就该由标签通路负责，而标签通路的召回比子串匹配准得多。

**不改 `search_text` 定义本身**，因为 embedding 需要标签——一句「一只很累的猫」对上库里的 `疲惫 猫`，正是向量路该干的事。变的只是 trgm 的匹配目标，见 [§5.2.3](05-data-models.md#523-ai-产出字段)。

## §9.22 语义维度拆成五个 · 2026-09-22 · accepted

**决定：`emotions` / `scenes` 两个维度拆成五个——`expressions`（面部表情）、`emotions`（情绪）、`tones`（表达语气）、`purposes`（聊天用途）、`scenes`（生活情境）。`tags` 不动。**

**触发它的是一张图：微笑角色配「你说得都对」。** 视觉事实是微笑，交流用途却是敷衍、是反讽。合成一个维度时，模型只能挑一个说，而它会挑最容易看见的那个——把这张图标成「开心、赞同」。**标完之后，这张图在库里的含义和它的实际用途正好相反。**

三对不能互相推导的东西：

| | |
|---|---|
| 微笑（表情） | 开心（情绪） |
| 「你说得都对」（字面） | 表面附和（用途） |
| 敷衍（不想聊） | 阴阳怪气（说反话） |

**v0.1.0 的 `scenes` 本身就是混的**：`拒绝`、`敷衍`、`吐槽`（交流动作）和 `加班`、`吃饭`、`打游戏`（现实场合）在同一个列表里。说明这个维度从一开始就在承担两件事，只是没拆开。

**放弃了什么：**

- **动漫 / 影视角色识别。** 「知道这是《XX》里的 YY 在做 ZZ」能带来更准的语义，但需要角色库、需要持续更新、多数情况下还要额外一次带检索的调用——成本和这个项目的定位不匹配。放弃它是产品负责人在 2026-09-22 明确决定的。维度拆分是同样问题的便宜解法：不认识角色，但认得出表情、语气和用途。**2026-09-29 被 [§9.34](#934-人物整图向量自动成组人来命名与合并系列是人工维护的父级--2026-09-29--proposed) 部分推翻（`proposed`）**：推翻的是「不做」，不是这几条理由——那边模型不认角色，只聚类，名字由人起。
- **一次调用的简单性没有放弃。** 仍然是单次视觉调用，只是输出多了三个数组。多出来的是提示词长度和输出 token，不是调用次数。

**代价：**

- 这是一次不兼容的词表变更（[§4.4](04-vocabulary.md#44-变更流程)）。存量记录的 `emotions` / `scenes` 里混着现在属于别的维度的值，必须靠迁移搬走。
- **推断维度会出错。** `tones` 和 `purposes` 不是视觉事实，是推断。起步只允许各取 0–2 个最有把握的，并且明写「证据不足留空」——猜出来的标签比空标签更坏，它会把不相干的图排到前面而用户无从得知。
- 词表规模从 3 个维度约 200 词涨到 6 个维度约 285 词，提示词变长。

**什么情况下该推翻：** 评测集显示 `tones` / `purposes` 的准确率低到不如不填（例如 `purposes` 的一致率不足五成），那说明这两维靠单次视觉调用推不出来，该退回到只标视觉事实，把交流意图留给 `description` 和向量路。**这件事必须由评测集判定，不能靠翻几张图看着顺眼。**

## §9.23 内容分级独立成第七维 `ratings` · 2026-09-22 · accepted

**决定：`memes` 新增第七个数组字段 `ratings`（内容分级），词表里目前只有「成人向」一个词条。库的可见性不变——标了成人向的图和别的图一样，默认对全部被邀请的人可见。**

触发它的是产品负责人 2026-09-22 的一句话：「现在标签没有色色，加上色色的标签，R18」。查证过，词表里当时确实一个相关词条都没有。

**为什么是维度，不是布尔字段。** 三个候选里选了这个：

| 方案 | 结论 |
|---|---|
| 塞进现有的 `tags` | 否。分级是「适不适合在这儿出现」，不是「图里是什么 / 长什么样」，混进去和 v0.2.0 刚拆掉的维度混装是同一类错误 |
| **独立成第七维** | **选它。** 两端读的都是同一份 `VOCAB_FIELDS`，校验、筛选、编辑 UI 全部自动跟着走；代价只有新列与一次 DDL |
| 独立的 `rating` 布尔/枚举字段 | 否。它能顺带做「默认隐藏 R18」，但那是**可见性**决策，不是分级本身；把两件事捆在一次变更里，会让一次词表变更变成一次权限变更 |

**这一维的真实来源是人工，不是模型。** [§9.5](#95-敏感内容双通道降级不是二选一--2026-09-13--proposed) 已经写明：境内受监管的模型对这类内容大概率在 API 层就拒绝，「这是合规问题，不是能力问题，调提示词绕不过去」。所以：

- 界面上不要把这一维呈现成「模型标好了的」；
- **模型拒了的图正好是最需要人工补标的那一批**（`refused` 的图「无语义描述，靠 OCR 和人工标签」，[§5.2.3](05-data-models.md)）。也就是说这一维和人工补标签的入口天然是一件事。

**放弃了什么：**

- **不细分。**「擦边」「露骨」「性暗示」暂时都不要，只有一个「成人向」。粒度细分是**兼容**的后续变更（[§4.4](04-vocabulary.md#44-变更流程) 的「新增词条」，可直接合入），想加随时能加；反过来先把细粒度塞进去再合并才是要迁移的。
- **不做默认隐藏。** 共享库里成人内容默认可见，这个代价 [§9.1](#91-库是共享的--2026-09-13--accepted) 已经接受过一次，本次不翻案。要隐藏就单开一次决策，它动的是读路径。

**代价：**

- 一次不兼容的词表变更：新列 + DDL 迁移，SPEC §4.3 / §5.2.6 / §6.3 同步，两端 `VOCAB_FIELDS` 同步。**没有存量要搬**——新列全空，旧记录没有值可搬，所以比「移动词条到别的维度」轻。
- 打标提示词从八个键变九个键。**老提示词 / 不认识这一维的模型缺席 `ratings`，按空数组处理，不是失败。**
- 提示词里多了一问「这张图是不是成人向」。**它对无害的图也问了**，而这可能提高整体被拒率——不只是 R18 那几张。这条没有实测支撑，只是推断。
- 按 [§4.4](04-vocabulary.md#44-变更流程) 改词表必须跑评测集，而评测集当前有前置欠账（标注还是 v0.2.0 之前的两维口径）。

**什么情况下该推翻：** 如果观测到加了这一问之后**整库**的打标被拒率显著上升（不只是成人向的图，连无害的图一起），就把 `ratings` 从提示词里摘掉、只保留人工编辑入口——词表和列留着不用，代价为零。判定它必须看真实拒绝率，不能看几张图。

## §9.24 全屏阅览器显示元数据 · 2026-09-22 · accepted

**决定：全屏阅览器底部加一条信息栏，显示标签值（`ratings` 排最前）、`description`（截断 2 行）、`@uploaderName`。不引入任何新字段。**

触发它的是 §9.23 落地后立刻暴露的缺口。查证时发现的问题比「R18 标签看不见」更大：**阅览器此前只渲染图片本身**（`src` / `alt` / 宽高），一条元数据都不显示；`MemeCard` 也从不显示标签值。全前端能看见标签值的地方只有筛选栏和编辑面板。于是「成人向」能存、能筛、能改，**就是看不见**——打开大图也不知道自己在看哪张。

**为什么是阅览器，不是卡片角标。** 两个场合的任务不同：网格是扫视，卡面小、密度高，角标会把每一维都变成一个反复出现的信号；阅览器是「已经决定要看这张」，元数据在那儿是补上下文。而且**这条不做可见性判断**——§9.23 已经明确把「默认隐藏 R18」单列成另一次决策，信息栏只是显示事实，不是警示。

**版式：贴合内容宽度居中，两侧留出可点背景。** 这不是审美选择。阅览器的「点背景关闭」只认 `event.target` 本身是 `.yarl__slide` / `.yarl__slide_wrapper` 的点击，一条铺满整宽、能接事件的底栏会把底部那条关闭区整条吃掉（单张阅览时左右翻页按钮当年就是这么坏掉背景关闭的）。贴合宽度之后，底部只剩中间一小块不可点，`Esc` / `×` / 下拉关闭三条路都还在。

**描述截断 2 行**（与 YARL 官方 captions 插件同一档，它是 3 行）。**阅览器里不能滚动**：`.yarl__container` 是 `touch-action: none`，且本仓开了 `closeOnPullDown`。所以截断不是美观取舍，是唯一选择——不截断的表现是长描述把信息栏顶到半屏高。

**不做：** 上传者名不可点。那会把它变成一个阅览器里的触摸目标（得按指针分档），而应用里并没有「某个人的图」这个页面——信息栏是纯展示，44×44 那条约束管的是触摸目标，不适用。也不声明任何标签的来源：§4.3 明确要求别把 `ratings` 呈现成「模型标好了的」，一条不作声明的扁平标签行正合那条。

**没突破 §5.2.6 的上限。** `tags` / `description` / `uploaderName` 三个字段早就在对外表示清单里，所以那句「这份清单就是展示全部图片信息的上限」不动——本次是**把已有字段摆到界面上**，不是往清单里加东西。

**什么情况下该推翻：** 如果信息栏让手机上「点背景关闭」变得难以命中（拇指自然落点正是中间那块），或者它盖住图上的关键信息（梗图的信息常压在底部），就退到只留标签行，或做成可折叠。**判定要靠在真机上试，不是看截图。**

> 这条与 §9.23 同日定下，但**是两件事**：§9.23 决定这一维怎么存怎么筛，本条决定已有的元数据在哪儿露出来。前者不做也是完整的（只是用户看不见），后者不依赖前者（任何一维都该显示）。

## §9.25 重打标跳过人工编辑过的图 · 2026-09-22 · accepted

**决定：`POST /memes/retag` 跳过 `edited_by` 非空的图，报 `skippedEditedCount`；不做「覆盖前先备份」「合并人工与模型结果」这类折中。入队与 `tag_status = 'pending'` 同事务；进度复用 `GET /memes/tag-status`，不另做端点。**

触发它的是 §9.23 落地后暴露的直接问题：词表多了第七维，而**库里的图是旧提示词打的**，没有任何机制让它们重跑。这个接口在 §6.4 的契约表里躺了很久、标着「尚未实现」，§6.6.2 还专门写了「不许在 §6.4 之外另造一个『重试』端点」。本次兑现它，并顺势把 §6.4 那句「用调用者自己配置的模型」改成与实现一致的「用上传者的」——**文档向实现靠拢是被迫的**：后台队列真的拿不到调用者，而反过来改代码要加列、改配置解析，不是一次改动的事（详见 §9.3 的更正）。

**为什么跳过，而不是覆盖或合并。** 九个字段是一次破坏性整体覆盖，`ocrText` 也在内。而人工编辑**没有任何自动留痕**——没有历史版本、没有「取消编辑」，一旦被冲掉就是不可恢复的。三个选项里：

- **覆盖**——让一次运维动作静默抹掉人做过的工作，而人做这件事的场合恰恰是「模型标错了」，也就是**人比模型对**的那些图。
- **合并**——需要定义「人改过的维度保留、没改的维度用模型的新值」，而库里的记录只知道 `edited_by` 非空，**不知道人改了哪一维**。真要做合并得先改数据模型存逐字段的编辑状态。
- **跳过**——代价明确且可陈述：这张图得不到新维度，出路是管理员 `PATCH` 手补。

选跳过。它和 §6.6.2 把「人工补」与「重跑模型」分成两条路的裁定是同一件事的落点：**机器输出不该冲掉人的工作。**

**已知的硬边界：被跳过的图会永久缺新维度。** `edited_by` 不会被清，仓里也没有「取消编辑」这条路。这不是可以顺手补的疏漏——要重跑它，前提就是接受人工编辑被覆盖，而那需要一次单独的决策。

**为什么不另做进度端点。** 重打**无状态**：它复用 `tag_jobs`，跑完之后库里没有任何「这张被重打过」的痕迹，也没有批次概念。专门造一个 status 接口，只能把 `tag-status` 已经在算的计数换个地方再说一遍——而 `web/agents/rules/settings-ux.md` 早就写了「数据来自 `GET /memes/tag-status`，不另做接口」。

**为什么按钮在设置页、为什么它不是「重建索引」的兄弟。** 两者相邻但**不相似**，这一点必须写在界面上：

| | `POST /admin/reindex` | `POST /memes/retag` |
|---|---|---|
| 花谁的钱 | 部署方的 embedding 预算（可忽略） | **图片上传者的**视觉预算 |
| 幂等 | 是 | **否**——再点一次就是再花一遍全库 |
| 界面可否允许重复点 | 可以，文案明说「重复触发是安全的」 | **不行**，要确认框 + 运行期间禁用 |

复用「重建索引」那套交互（点一下就跑到天荒地老）会把这条差别静默掉，而它的代价是真金白银。

**连带接受的一条：全库会短暂变成「待打标」。** 选型要求入队即置回 `pending`，所以重打期间每一张卡片都带角标、`?tagStatus=ok` 的视图会短暂变空。这是**进度唯一可见的来源**，不是副作用——不置回 `pending` 的话界面在整段时间里一动不动。代价记在 [§6.4.3](06-endpoints.md)。

**什么情况下该推翻：** ①如果在真实使用里「跳过人工编辑过的图」导致这些图长期缺维度、而管理员补起来太烦，就该做**逐字段的编辑状态**（存人改过哪几维），然后把跳过改成合并——这是一次数据模型变更，不是策略调整。②如果 `retag` 被频繁用于「单张图重试」，那就该在卡片上加「重跑模型」入口，`memeIds[]` 那个形状就是为它留的。③如果重打的等待时间在实践中不可接受（`PER_USER_INFLIGHT = 1` 让单用户库的吞吐退化成 1 条/次，75 张约 9–20 分钟），那要论证的是**并发分配规则**在单用户库上的退化，不是这个接口。

> **评测集跑不了**（标注还是两维口径的前置欠账），所以「重打之后 `ratings` 准不准」**没有数据**。另外提示词对无害的图也多问了一问，可能抬高整体拒答率——§9.23 记着这条无实测支撑，而**一次全库重打是第一次能量出这个数的场合**。样本量不足以判定，只能当观察记。

## §9.26 并发参数归运行期配置，产品语义参数留常量 · 2026-09-23 · accepted

**决定：把四个「保护机器」的参数（打标并发、每用户在途、导入管线并发、ffmpeg 子进程上限）从模块级常量改成 [§5.6](05-data-models.md) 的单行表，由 `admin` 在设置页的管理员分段改，改完**不用重启**、对新任务生效。帧数、送 AI 的长边、拼图帧数、两个去重阈值仍然留在 `image/constants.ts`。**

触发它的是 [§9.25](#925-重打标跳过人工编辑过的图--2026-09-22--accepted) 末尾写下的第三条推翻条件：`PER_USER_INFLIGHT = 1` 让**单用户库**的吞吐退化成 1 条/次，第二个槽空转，75 张要 9–20 分钟。那条记录已经指出「要论证的是并发分配规则在单用户库上的退化」，本条就是那次论证的结论。

**划线判据：这个参数改变的是产出，还是吞吐？**

`image/constants.ts` 的文件头原先写的是「是常量，不是环境变量——部署方没有理由调它们，放进 env 只会让『多图上限到底是几』变成每个部署都不同的谜」。**这句话对一半。**

| 参数 | 改它改变什么 | 归谁 |
|---|---|---|
| `MAX_FRAMES` / `AI_LONG_EDGE` / `COLLAGE_FRAMES` | 模型**看到**什么 → 标出来的结果 | 常量 |
| `FRAME_DEDUP_DISTANCE` / `NEAR_DUP_DISTANCE` | 什么算重复 → 用户要在待确认队列里处理多少条 | 常量 |
| 打标 / 导入 / ffmpeg 并发、每用户在途 | 只是**多快**跑完 | 运行期配置 |

前一类换一个部署就该是同一份，**因部署而异才是真正的问题**——原话针对的正是它们，成立。后一类恰恰相反：机器规格因部署而异，一台 2 核小机器和一台 16 核机器需要不同的上限，而原来的写法是「改一次要改代码 + 重新部署」，这与本项目「边用边迭代」的节奏直接冲突。

**为什么是数据库，不是环境变量。** 环境变量只在进程启动时读一次（`api/src/env.ts` 是模块级单例），**「不重启就生效」这件事靠 env 根本做不到**——那正是本次的需求。而且 [env-validation.md §1](../api/agents/rules/env-validation.md) 规定校验过的 `env` 之外不再出现 `process.env`，加四个变量要把它们拖进那份校验与 `docs/environments.md`，换来一个「改了也不生效」的旋钮。

**为什么不需要新机制。** 本项目既有做法是**不缓存、每次用之前查一次库**：视觉通道（`PUT /config/vision` 写完，打标 worker 每轮 tick 调 `isVisionConfigured()` 现查）和 Embedding 通道（重建 worker 每轮 tick 调 `isEmbedConfigured()`）都是这样，且都在 `server.ts` 的注释里写明了「配好之后不需要重启进程」。运行参数走同一条路。**不引入进程内事件通知**——worker 不假设单副本（[queue.md §1](../api/agents/rules/queue.md)），进程内通知到不了别的进程，读库才能到。

**已知偏差，不打算修：所有并发都是「每进程」的。** 多副本时全局上限 = 配置值 × 进程数。真正的全局上限需要分布式限流，而本项目不引入 Redis（[§9.11](#911-不引入-redis队列和会话都用-postgresql--2026-09-13--accepted)）。这与「不假设单副本」不冲突：那条管正确性（不重复消费），这条管节流。**但界面措辞必须按「每个服务进程」说**——写「全站最多 N 张」在多副本下就是假的。

**越界报错，不静默截断。** 这个仓已经因为「静默」吃过几次亏（`retag` 对已 `done` 行的入队是静默空操作、`filter.uploader` 的形状校验排在角色判断之后、`enqueuedCount` 这个名字让人写 `=== true`）。静默截断的表现是「填了 16、保存成功、回显 2」，比报错难查得多。

**本次没做，也不该顺手做：**

- **重建索引并发、任务整体超时、空转轮询间隔**仍是常量。超时与轮询属于故障处理参数，而它们之间有硬关系——`STALE_RUNNING_MS` 必须明显大于 `JOB_TIMEOUT_MS`，否则会把正在跑的任务抢走、同一张图被调用两次 AI。两个可以独立调节的数，迟早有人把它们调反，而表现是**同一张图付两次钱**。
- **每用户配额**不做成这个表的一项。存储配额（`users.storage_quota_bytes`）是每人的，这里的并发是全站的，两个概念不合并。
- **不为「立即生效」打断在途任务**——那会留下永远停在 `running` 的行，见 [§6.5.5](06-endpoints.md)。

**什么情况下该推翻：** ①如果实践中管理员调参调错的次数比它省下的时间更值钱，就该把上限收窄成「几档预设」而不是自由填数。②如果真要跑多副本，得先把并发计数、SSE 广播（`services/import-events.ts` 明确写了是进程内广播）和这套「每进程」语义一起重新论证——那是三件事，不是一件。③如果 `NEAR_DUP_DISTANCE` 在实践中被管理员要求「按库的规模调」，那说明划线判据错了，得重新划。

**这条为什么还不到 `stable`：** 两端实现都已落（api 425 条测试全绿、web 在真 Chrome 里过了两档视口），但 web 侧的全部断言都是对着**按 api 实现逐字校准的替身**跑的，**两端从未对话**。这正是 [模型配置任务](../_archive/joint-tasks/2026-09-16-ai-config.md) 第一轮判不通过的那种状态——那一次真接上之后立刻暴露了两处偏差。转 `stable` 的条件是真 api × 真浏览器跑一次，见[运行参数任务](../joint-tasks/2026-09-23-runtime-config.md)的「总管裁定」。

## §9.27 评测集不阻塞核心功能 · 2026-09-24 · accepted

**决定：把[评测集](../joint-tasks/2026-09-13-eval-set.md)、[词表 v1](../joint-tasks/2026-09-13-vocab-v1.md)、[供应商探测](../joint-tasks/2026-09-13-provider-spikes.md) 三件事从「写核心代码之前必须先做」改成并行推进：先按 `proposed` 版本落代码，用起来再拿数据验证。约束落在交付上——动了提示词、词表或检索参数，**必须说明有没有跑评测集，没跑就说没跑**，不允许用「看着没问题」代替。**

这条推翻的是 [§9.12](#912-起待验证项--2026-09-13--proposed) 开头那句「必须在写核心代码之前跑掉」。那句话没被删掉——它记录的是当时为什么这么想。

**放弃的是什么。** 放弃一次把打标质量校准到位的可能，而且代价是长期的：**没有评测集，词表和提示词的每一次改动都没有对照物**，「改完是变好还是变坏」只能靠肉眼，样本量小时几乎无法分辨。最具体的例子是 [§9.23](#923-内容分级独立成第七维-ratings--2026-09-22--accepted) 的 `ratings` 维度——它靠人工编辑兜底，模型侧准不准**一个数字都没有**；那一维的提示词还多问了一问，是否抬高整体拒答率同样没有实测支撑。

**为什么这样划算。** 三件事的真实门槛不是钱（评测集几毛钱），是**它们都要求先有一批真实的表情包和真实的 key**。30 张标注、各家供应商的拒绝形态，都要拿真图真 key 去跑；库是空的时候它们只能对着构造样本做，做出来的数字不能代表生产。所以「先有库、再评测」不是偷懒，是拿到有效数据的**唯一**顺序。坚持前置的实际结果已经看到了：核心功能停在「等评测」，而评测因为库是空的也做不了——[评测集任务](../joint-tasks/2026-09-13-eval-set.md) 从 2026-09-13 挂到现在就是这个状态。

**什么情况下推翻：** ①出现「连续两次改动都无法判断是否变好」时——那说明凭直觉迭代到头了，必须先把评测集跑起来；②打标质量的抱怨开始集中出现时；③要横向推荐某个供应商的配置时（[§9.8](#98-默认推荐配置与模型选型--2026-09-13--proposed) 一直卡在这里，没有评测就没有推荐依据）。

## §9.28 状态标记记的是契约是否对齐，不记实现进度 · 2026-09-24 · accepted

## §9.29 检索并进列表端点，检索改为可翻页 · 2026-09-26 · accepted

**决定：`GET /memes` 成为唯一列表端点并吸收 `q`；有 `q` 时在**筛后的候选集**里做三路召回 + RRF 融合，而且**可以翻页**。`GET /search` 冻结成 `≡ GET /memes?q=` 的子集（只认 `q` 与 `limit`，不分页），不再演进。首页本轮不动，它的去向（产品负责人指向「像浏览器首页一样」）另开任务。**

契约落点：[§1.3](01-http.md)（取消「搜索接口不分页」）、[§6.3](06-endpoints.md)（合流成两种排序语义、加 §6.3.3）、[§2.2](02-errors.md)（游标类错误走 `VALIDATION_FAILED`）。三节与本节同批：当天写成 `proposed`、两端读过并确认后同批转 `accepted`。任务与裁定过程见[检索与筛选合流](../_archive/joint-tasks/2026-09-26-检索筛选合一.md)。

**这条推翻「搜索不分页」。** 原话是「三路融合后只返回前 N 条，默认 50、最大 100。用户只看前几个结果，翻页没有意义」，写在 §1.3、[§6.3.1](06-endpoints.md) 和 [`api/agents/rules/retrieval.md` §6](../api/agents/rules/retrieval.md)。它**没有进过 §9**，所以没有 §9 条目要标 `deprecated`——原话记在上面这一行，那三处按 [§8.1](08-collaboration.md) 直接改写。产品负责人 2026-09-26 明确推翻，并允许改契约、允许产品形态变化。

**合并的另一半不是翻页，是「筛完还能搜、搜完还能筛」。** 今天两条路径完全独立：搜出「今天真的不想上班」之后想再收窄到「猫」，只能去浏览页按标签筛**全库**，等于重新找一遍；反过来在浏览页筛着筛着想说一句人话，没有入口。这一半不需要分页机制也能成立，但两半得在同一个 URL 上才是一件事——**能筛的列表能翻页、能搜的列表不能翻，是站不住的**，所以合流是主线，翻页是它的必然结果。

**放弃的是什么。** ①放弃一个便宜得多的实现：按 2026-09-26 读代码确认，融合池本来就是「三路各取 top-N 的并集」（≤150 条），只是被截断到 100——**只把截断放开，深度就能从 1 屏变成 4 屏，代价是一个常量**。选了真无限就得付快照、生存期、以及「每往后翻一片要按新深度重扫三路」。这是看清代价后的选择，不是没看见。②放弃「深度真的无界」的直觉：契约不设深度上限，但每条通路的候选池是有代价的，深度只能靠不断放大重扫换来，**筛得越窄越早到底**。③放弃「一次检索等于全库现状」：快照期内新上传的图不出现在后续页里——那是快照方案的定义，不是缺陷。

**为什么划算。** 共享库的价值是「翻出来有用的那张」，不是「按标签翻全库」。旧立场（只看前几个）从来没有被测过，而它造成的具体损失指得出来：筛和搜不能叠加，等于每次从全库重新开始。

**什么情况下推翻：** ①如果实测下来没人翻过第二屏（前端能数翻页请求的占比），这套快照机制就该退回去，检索分支回到「单次返回融合池」，也就是上面「放弃的是什么」第①条那条便宜路。②如果「筛得越窄越早到底」在常用筛选组合上频繁发生，说明瓶颈不是深度而是**筛后集合的大小**，那时要谈的是筛选维度怎么组合，不是继续加深。③如果快照的生存期与清理在实践中成为故障源（本仓的定时任务目前是零实现），先解决清理再谈加深。

## §9.30 首页 = 入口页：搜索只做入口，主体是图墙 + 两条 rail · 2026-09-26 · accepted

**决定：首页不渲染搜索结果。搜索框保留，但只做入口——提交即导航到 `/browse?q=`。首页的主体是「随便看看」随机图墙（全库随机 + 换一批）、两条 rail（我的收藏、最近上传，各 8 张 + 「查看全部 →」）、以及只在真有货时出现的待处理状态条。老链接 `/?q=…` 重定向到 `/browse?q=`。**

契约落点：本节（新条目）、[`web/agents/rules/state-navigation.md` §4/§6](../web/agents/rules/state-navigation.md)（`/` 那行定论、§6 那张接口表）。**本任务零接口改动**：图墙继续走 [`§6.3.2`](06-endpoints.md) 的 `random=true`，两条 rail 就是 `GET /memes` 的两个现成参数（`favorited=true` / 默认序），状态条读 [`§6.6.1`](06-endpoints.md)。`GET /search` 因此**失去唯一消费者**，它的删除是同一任务的第二段（[`§6.3.3`](06-endpoints.md) 整节 + [`§1.3`](01-http.md) 那条「缺省 50」的例外），**等 web 端合入并验收之后再动**——顺序反了会当场打断首页。任务与裁定过程见[首页改版](../joint-tasks/2026-09-26-首页改版.md)。

**为什么。** [`§9.29`](#929-检索并进列表端点检索改为可翻页--2026-09-26--accepted) 定下「检索并进 `GET /memes`」时写明了首页本轮不动、去向另开。合流之后，首页那段结果成了一条**更差的重复列表**：同一句话，在 `/` 上不能筛、不能翻页，在 `/browse` 上能筛能翻。它存在只是因为 `/search` 还没死；要继续留着它，就得回答「为什么同一件事有两个入口、其中一个残」——答不上来。而首页空出来的那一半内容职责（「不知道要找什么的时候随便看看」）今天没有替代物：浏览页有游标、有筛选、有排序，**没有随机**，「把三个月前那张图翻出来」只有 `random=true` 这一条路。

**放弃的是什么。** ①放弃「首页继续自己渲染结果」：那要么让首页长成一个残废的 `/browse`，要么把筛选和翻页也搬上首页——两个列表页，正是 §9.29 花整条决策消掉的东西。②放弃「图墙挪去 `/discover`、首页只留一个搜索框」：那会让首页变成一扇没有内容的门，而随机图墙恰恰是**唯一需要「第一屏就看见」**的内容——它不是某个功能的结果，它是「不知道要找什么」时的入口本身。③放弃「首页做成工作台（状态与动作优先）」：那会把第一屏给上传者 / 管理员（待处理、失败、配额），而「就想找张图逗人笑」才是主场景，**多数用户多数时候没有待处理**——工作台对他们是零信息，对少数人也不是每天都要看。

**代价。** 首页不再能回答「搜到没有」——提交之后人就走了，所以**首页不能有任何「只有键盘到得了」或「只有键盘到不了」的入口**（图墙那枚发送键因此是看得见的普通按钮，见 §9.31）。顺带认下一条：`?q=` 的老链接（分享出去的、书签里的）从此都靠一条重定向活着，删它等于把那些链接变成 404。

**什么情况下推翻：** ①如果绝大多数搜索都从首页发起、却在 `/browse` 上空手而归，说明「交棒」这一步太远，那时要谈的是首页要不要就地给一个**轻量**的命中预览（不是把结果区搬回来）。②如果随机图墙的使用率显著低于两次 rail（前端能数「换一批」的点击占比），说明第一屏该换个内容，而不是把搜索搬回来。③如果 `/?q=` 的重定向在实际流量里占比长期很高（说明分享链接的旧地址广泛存在），那要谈的是重定向要不要保留更久，不是回滚改版。

**落地（2026-10-01）：** 两段都已合入。web 段先上（首页不渲染结果、搜索交棒 `/browse?q=`），api 段随后删掉 `GET /search` 与 [§6.3.3](06-endpoints.md) 整节；那个「`limit` 缺省 50」的例外随端点一起消失，列表端点现在只有 [§1.3](01-http.md) 一份默认值（40）。本条与 [§9.31](#931-首页图墙卡片的动作只有发送不挂菜单--2026-09-26--accepted) 由两端读过之后同批转 `accepted`（[§9.28](#928-状态标记记的是契约是否对齐不记实现进度--2026-09-24--accepted)：状态记契约对齐，不记实现进度；真链路联合验收仍欠着）。

## §9.31 首页图墙卡片的动作只有发送，不挂「⋯」菜单 · 2026-09-26 · accepted

**决定：首页「随便看看」图墙的卡片，`actions` 槽里放**一枚直接发送按钮**，不挂 `MemeActions` 那个「⋯」菜单。全屏阅览器里那枚发送按钮保留。首页两条 rail 的卡片上**一枚浮层按钮都不给**（连收藏也不给）。**

契约落点：本节（新条目）、[`web/agents/rules/clipboard-share.md` §3](../web/agents/rules/clipboard-share.md)（发送入口总表 + 那条偏离的边界）。这是对[检索筛选合一](../_archive/joint-tasks/2026-09-26-检索筛选合一.md) §3 **裁定 4**（「一个动作只出现一处」、发送统一走「⋯」菜单那一项）的**明写偏离**。

**为什么偏离。** 裁定 4 的语境是**合并后的列表**：那里卡片同时需要编辑、删除、发送，所以菜单是对的。而图墙**没有编辑也没有删除**——它是「随便看看」，不是管理面（没有归属逻辑可讲，也不该在随机翻出来的图上出现删除入口）。为了一枚按钮挂一个只有一项的菜单是净负担，而发送是这个产品的核心动作、要一击可达。

**偏离的边界，以及它为什么必须写下来。** 「哪一屏该有」的判据是**那一屏有没有管理面**，不是「卡片都长得一样」。所以：图墙有那枚按钮，两条 rail 没有（连收藏也没有——rail 是预览，要发送就点开或去 `/browse`）。写下来的原因正是**这种偏离最容易被后来者「统一」掉**：看到图墙有、rail 没有，很容易判断成漏了。

**放弃的是什么。** 放弃「卡片上的动作一律从菜单进」这条整齐的规则。代价是**同一个动作的入口形态在两屏上不同**——但它指的仍然是同一个函数（`lib/clipboard.ts` 的 `sendMeme` → `sendNote` → `notifySend`），分流只看 `isAnimated` 与能力探测，所以「一个按钮两种行为」那条真正的红线没有被碰。

**什么情况下推翻：** ①如果图墙上迟早要长出第二个动作（比如「收藏」之外的举报 / 编辑），那菜单就该回来，这一条随之作废。②如果实测里图墙那枚按钮的误触率明显高于菜单项（点开的人多半不想要发送），说明「一击可达」在这个位置是负收益。③如果 rail 后来也需要发送（产品上确有必要），那时该谈的是「rail 要不要变成图墙的同一种」，不是给 rail 单独补一枚按钮。

**决定：[§3.2](03-auth-permission.md) 那句「第一个注册的用户自动成为 `User`」不改。不加 `BOOTSTRAP_TOKEN`，不做建号 CLI。上线前后的空窗期写进[部署手册 §9.4](../docs/deployment.md)：反代一通立刻注册，注册完用 SQL 核对第一行是自己，不是就清空重来。** 产品负责人 2026-09-26 裁定，出处是[会话与访问收口](../joint-tasks/2026-09-24-auth-access-hardening.md) §4 第 1 条。

## §9.33 近似重复：距离 0 直接判重，其余交给打标通道的视觉模型，模型拿不准才进待确认队列 · 2026-09-29 · accepted

**决定：入库管线在 SHA-256 之后的近似重复判定改成三档，替代 [§9.7](#97-系统不替用户猜能力靠实测近似重复靠人判断--2026-09-13--accepted) 里「近似命中一律进待确认队列」的那一半。** 产品负责人 2026-09-29 提出，动机是真实数据：一次导入 500 多张，待确认队列里**绝大多数是 Hamming 距离 0**，逐条点「跳过」不是「让人看一眼」，是纯体力活。

| pHash 最近邻距离 | 处置 | 判断权 |
|---|---|---|
| 无（超过 `NEAR_DUP_DISTANCE`） | 入库、打标（不变） | — |
| `= 0` | **直接判重复**：跳过、删暂存对象，条目 `result = exact_dup` | 机器 |
| `1 … NEAR_DUP_DISTANCE` | 调**上传者的视觉通道**（与打标同一条，`resolveVisionConfig(userId)`），把两张图一起给它问「是不是同一张」 | 视觉模型 |

视觉模型的答案是**三态**，不是二态：

| 答案 | 处置 |
|---|---|
| `same` | 判重复：同距离 0，`exact_dup`，跳过、删暂存对象 |
| `different` | 不是重复：**继续往下走入库、打标**，与近似命中不存在时一样 |
| `unsure` / 调用失败 / 超时 / 输出不合法 / 没配视觉通道 | **降级为原来的待确认队列**（`needs_review`），交给人。**永远不因为模型出问题而让条目 `failed`，也不因此默默入库** |

**放弃的是什么。** [§9.7](#97-系统不替用户猜能力靠实测近似重复靠人判断--2026-09-13--accepted) 的原话是「近似重复交给人判断」。这一条把**两段**交给了机器，并且**判重复的那一支不可撤销**——暂存对象被删，用户没有机会看到被丢掉的那张。所以：

1. **距离 0 判重是明知有误判风险的取舍。** pHash 取的是缩小后的低频成分，「同一模板换了字」在低频上可能完全一致、距离恰为 0。这类图会被静默丢掉。接受它的理由是：真实数据里 0 距离以「重新编码 / 换压缩 / 换尺寸的同一张」为主，误判率要靠使用来量，见下方「什么情况下推翻」。
2. **视觉模型这一档偏向保守。** 三态里 `different` 与 `unsure` 的分界，提示词要写成「只要有任何可见差异（文字、表情、构图、局部）就不是 `same`」；拿不准一律 `unsure`，不许硬凑二选一。理由沿用 `NEAR_DUP_DISTANCE` 注释里那条不对称：**误丢一张不同的图是不可恢复的，多让人看一眼只是一次点击。**
3. **所有自动判重的条目必须留痕**：`import_items.meme_id` 指向被比中的那张，`distance` 写入实测距离，`reason` 写明依据（「画面完全相同（距离 0）」或「视觉模型判定为同一张：<模型给的一句理由>」）。事后要能回答「这张为什么没进库」。

**代价。** 距离 1–8 的每一次命中多一次视觉调用（两张图，花的是**上传者自己**的额度）；调用发生在导入管线并发槽里，会拖慢那一批。`exact_dup` 的语义从「字节完全相同」放宽为「库里已有这张」——**这是字段语义变更**，按 [§8.3](08-collaboration.md) 归不兼容，web 端「跳过 N 张完全相同的文件」那句文案必须一起改。

**没有开关。** 不为它加运行参数或用户设置：想回到全人工，改 `NEAR_DUP_DISTANCE` 之外没有别的入口，这是有意的——多一个开关就多一种「同一张图在不同用户那里结果不同」。如果实测发现需要，再开新决策。

**已经在队列里的存量条目不受影响**——本决定只改**新导入**的判定。存量的处理见[任务文件](../joint-tasks/2026-09-29-近似重复自动判定.md) §4。

**什么情况下推翻：** ①发现距离 0 的误判（用户发现某张图「导入了却没进库」且确实是不同的图）出现过一次以上——回到「距离 0 也进队列」，把「一键跳过所有距离 0」留给用户自己按；②视觉模型的 `same` 与人的判断明显不一致（抽样对照）；③视觉调用成本让用户不满。任一条出现就回到 §9.7 原样。

## §9.34 人物：整图向量自动成组、人来命名与合并，系列是人工维护的父级 · 2026-09-29 · proposed

**决定：每张图用图片向量模型算一个整图向量；新图离已有的某个人物足够近就挂上，否则自成一个未命名人物。命名、合并、移出、隐藏、归系列全由人做。系列是人物的父级，只由人挑选人物组成，一个人物至多属于一个系列。** 契约落点 [§5.7](05-data-models.md)、[§6.7](06-endpoints.md)、[§6.3.2](06-endpoints.md) 的 `person` / `series`。方向由产品负责人 2026-09-29 拍板，两轮探测数据见[任务](../joint-tasks/2026-09-29-人物识别与聚类.md) §9。

> **2026-09-30 · 实测警告（本次没有改本条正文）**：真实库上出现大面积混簇（「明明不是他说是」），实测确认**不是阈值没调对**——这个库上不同角色能到 **0.90**，同一个角色换了画风只有 **0.56–0.80**，**信号是反的，不存在能分开它们的阈值**；质心规则又把最大那组变成 hub（61 个成员**全部**在质心 0.829 以上，而彼此最低只有 0.629，所以「过 0.825 就挂」在这个库里几乎恒真）。**推翻条件 1 已经触发**，而且它给的那条退路（「只给建议、不自动挂」）依赖的是同一个坏信号。146 个人物与 1485 条队列已清、288 条向量保留，**自动挂那一小块还在代码里**。本条仍是 `proposed`，**路径重定待议**：证据、成本与全部问题点见[任务](../joint-tasks/2026-09-29-人物识别与聚类.md) §13。**2026-10-01 起该任务暂停**，功能已在界面上**全部隐藏**、机器自动挂由 api **下掉**（暂停期间的收口，**接口与契约都留着**，撤掉即放开）——见[人物与系列：暂停期间临时下线](../joint-tasks/2026-10-01-人物功能临时下线.md)与任务 §13.6 ⑫。

**它部分推翻 [§9.22](#922-语义维度拆成五个--2026-09-22--accepted) 的「放弃动漫 / 影视角色识别」，推翻的是「不做」，不是那几条理由。** 那几条理由——要角色库、要持续更新、要带检索的调用——说的都是「让模型认出这是谁」。这里模型谁也不认识，只回答「这两张像不像同一个」，名字由人起。角色库的位置被人工命名占了，所以那三笔成本一笔也没回来。

**放弃了什么：**

1. **裁剪 / 画框。** 探测里头部裁剪、身体裁剪都不比整图好，画框还要求用户的视觉通道能返回坐标。代价：多个角色同框的图只能归一个人物。
2. **让视觉模型判灰区。** 224 对灰区里它说 `same` 44 次，错了 9 次，错法与向量同类（同发色 + 猫耳）。所以它不进判定，也不进建议排序。这与 [§9.33](#933-近似重复距离-0-直接判重其余交给打标通道的视觉模型模型拿不准才进待确认队列--2026-09-29--accepted) 用视觉模型判近似重复不矛盾：那边问的是「是不是同一张图」，可见差异是硬证据；这里问的是「是不是同一个角色」，模型和向量看的都是外观，两个同源的证据叠在一起算不上交叉验证。
3. **机器自动合并。** 阈值取探测里零混簇的那一档。代价是同一个角色换了画师、画风，大多会碎成几组，只能靠人合并。不对称的理由：误合并让按人物筛混进别的角色，碎片只是多一格。
4. **全站「待合并清单」。** 模拟里按组给建议（「这一组最像哪一组」）在挂簇阈值下 12.7 / 12.7 全对。排成全站清单时，收前一半碎片一条错的都不用点，拖尾却要点掉 68 条错的才收得全。所以只做按组的建议，不承诺清空。
5. **合并撤销。** v1 不做，合错了靠把图移出来修。
6. **系列多对多。** 联动角色只能挂在一个系列下。

**为什么这笔交易划算：** 人物的所有写操作都不调 AI（建议从已存的向量算），所以能像标签一样对所有人开放，不会开出一条任何人都能走的烧钱路径（对比 [§9.19](#919-人工编辑不触发向量重算--2026-09-19--accepted)）。图片向量走一份全站配置、花部署方的额度，因为向量要能互相比，与 [§9.6](#96-embedding-必须全站统一共享库的最大技术约束--2026-09-13--accepted) 是同一个约束。

**代价：**

- 每张图一次付费的图片向量调用；存量第一次补跑要管理员点、点之前问。
- **向量对输入尺寸敏感**。改送入的长边等于换向量空间，要全量重算。
- **非人物的图也会成组**：猫、纯文字、同一模板。v1 不按标签预筛，靠「隐藏」收拾，真库的比例没量过。
- **真人一张都没测**，两轮探测全是二次元。

**什么情况下推翻：**

1. ~~真库里混簇（一个人物里混进别的角色）不是个例：先收紧阈值；还不行就改成「只给建议、不自动挂」。~~ **2026-09-30 已触发，且「先收紧阈值」这条路已排除——见本条开头的实测警告：信号是反的，不存在能分开的阈值。**
2. 真人组的同人相似度落进不同人之间：真人改走另一条路（云端人脸比对，任务 §4 第 5 项），二次元保留本条。
3. 500 张规模下按组建议的命中率明显掉下来：重新考虑让视觉模型给建议排序。
4. 联动角色多到一人一系列不够用：系列改成多对多。

## §9.35 MCP 接入：进程内、无状态双模、PAT 只读 · 2026-10-22 · accepted

**决定：在 `api` 进程内新增只读的 MCP 端点 `/mcp`，无协议级会话，同时服务 2026-07-28 与 2025 代客户端；用个人访问令牌（PAT）鉴权；工具优先返回 R2 公开 URL，图片字节只做可选缩略图内联；本期同时提供 web 设置页管理令牌。** 契约落点 [§10](10-mcp.md)、令牌模型 [§5.8](05-data-models.md)、管理端点 [§6.8](06-endpoints.md)。四项边界（只读 / PAT / 设置页 / 默认挂载）由产品负责人 2026-10-22 拍板。

**为什么在 `api` 进程内，不新建服务。** MCP 工具的每一次检索都要复用 `data/memes.ts` 的软删过滤、`services/search.ts` 的三路召回与 HyDE、`serialize/meme.ts` 的字段裁剪——这些是[三条硬边界](../AGENTS.md)与检索口径的唯一入口。单独起一个 MCP 服务意味着把访问层复制一份，或者给 `api` 开一条内部 RPC；前者必然分叉，后者多一个部署单元和鉴权层。新规范的 MCP 是**无状态**的，独立扩缩容本来也没有收益。

**为什么是 SDK v2 + 双模。** 2026-07-28 删掉了会话与 `initialize`；而 2026-10 市面上的客户端大多仍是 2025 代。SDK v2 的 `createMcpHandler` 默认 `legacy: 'stateless'`，同一个工具工厂同时服务两代，且天然按请求无状态——与「不引入 Redis」「不假设单副本」[§9.11](#911-不引入-redis队列和会话都用-postgresql--2026-09-13--accepted) 是同一组约束。**放弃 v1**：v1 的会话形态要自己存会话与事件流，等于给这个只读接口加一层与项目不符的状态。

**为什么先 PAT，不上 OAuth 2.1。** 规范里 authorization 是 OPTIONAL；理论上 OAuth 是最"正统"的，但它要 AS 元数据、资源元数据、PKCE、DCR/CIMD、audience 校验五件套，工作量是 PAT 的 5–10 倍。真实需求是「自己的 Claude / Cursor / Cherry Studio 能连上自己的库」，而这些客户端都支持自定义 `Authorization` 头。**代价照实认下**：`claude.ai` connectors 那类只走 OAuth 的宿主直连不了，要么用 stdio 桥，要么以后另立 OAuth 决定。静态 Bearer 不是规范定义的流程，会随客户端变化——所以 `docs/mcp.md` 必须写清这一点，不做"全客户端可用"的承诺。

**为什么只读。** MCP 的价值是「聊天时拿一张图」，不是「让模型管理库」。写操作会同时引入归属判断、成本（重打标花上传者的钱）与不可逆破坏，而这三样在共享库里都属于[§3.4](03-auth-permission.md#34-实施要求)明确要收口的地方。只读让令牌的风险上限等于"member 能读全库"——那本来就是设计本身（[§9.1](#91-库是共享的--2026-09-13--accepted)）。

**为什么 URL 优先、base64 只做缩略图。** IM 渠道的输入全是"服务端能拿到的东西"：LINE 强制两个公网 HTTPS URL，钉钉群 webhook 只能 markdown 内联 URL，QQ 机器人支持把 URL 交给平台换 `file_info`，飞书 / 微信要由机器人下载后换 key；没有一个渠道接受 MCP 响应里的 base64 当输入。而聊天客户端只有 `image` content 能直接显示，可原图 base64 会撞客户端工具输出的体积上限。两条合起来只剩一个解：**`url` 保证"能发出去"，小缩略图 base64 保证"LLM 客户端里能看见"**。这也意味着 R2 公开桶是这项能力的部署前提，不是可选优化。

**成本与节流是一等公民。** 一次未命中的语义检索 = 1 次 HyDE（搜索者本人视觉通道）+ 1 次查询 embedding（全站配置）；群聊场景下按消息触发会把部署方的 embedding 额度与用户自己的视觉额度同时打上去。所以有令牌级限流 + 进程内 60 秒结果缓存 + 查询/条数上限。**缓存不落库**：它只是挡重复查询的短命缓存，不是第二份检索快照；多副本各缓存各的，与「不引入 Redis」一致（[§9.11](#911-不引入-redis队列和会话都用-postgresql--2026-09-13--accepted)）。

**放弃了什么：**

1. **独立 MCP 服务 / 独立容器**——复制访问层或加内部 RPC，收益抵不过成本；MCP 无状态，也不需要独立扩缩容。
2. **给 REST 全面加 Bearer**——那会扩大攻击面并把「两种凭证」的复杂度扩散到每个端点；v1 只在 `/mcp` 认令牌。
3. **OAuth 2.1 + DCR + CIMD**——见上；`claude.ai` connectors 用 stdio 桥过渡。
4. **写工具 / 管理工具**——见上；不是遗漏，是边界。
5. **`resources` / `prompts` / 变更通知 / MCP 会话**——本用例只需要工具，多一套原语就多一套契约与测试面。
6. **图片代理 / 转码端点**——会把图片字节拉回 `api`，与「图片字节永远不经过 api」相撞；渠道格式适配归机器人。
7. **仓库内实现微信 / QQ / LINE bot**——外部资质与合规问题，个人号没有官方 API。MCP 是接入面，bot 是调用方。

**代价：**

- 多一个对外接口与一份令牌表；令牌管理需要一个 web 设置页（[§10.8](10-mcp.md#108-文案契约)）。
- 令牌是长期凭证，泄漏即等于该用户的只读身份；靠一次性显示、可撤销、每人 10 个上限与日志不落值来收口。
- **不给 OAuth 的宿主直连不了**；没有"扫码授权"这种体验。
- 工具输出里带用户上传图片的 OCR / 描述，属于不可信文本；靠固定声明 + 截断 + 结构化返回降低提示词注入面，但**不能声称根除**（模型无法区分数据与指令）。
- 每次语义检索仍有一次外部调用，限流与缓存只能压频率，不能消除成本。

**什么情况下推翻：**

1. 主流客户端迁到只支持 OAuth 的远程 MCP（`claude.ai` connectors 成为主入口）→ 补 OAuth 2.1 + RFC 9728，PAT 降为"开发用"。
2. 缓存 + 限流仍挡不住成本（令牌被盗用、群聊高频触发）→ 把限流改成按用户 + 按日配额，并考虑共享存储。
3. IM 渠道实测表明 URL 方案不可用（例如某主渠道只收上传后的 media id 且不开放 URL 下载）→ 重新评估机器人侧代理，而不是在 `api` 开图片代理。
4. SDK v2 与真实客户端出现无法绕过的兼容问题 → 用 `isLegacyRequest` 接 v1 的会话式回退，或整体回退 v1（此时同步修本条）。

## §9.36 MCP 内容范围与上下文成本：成人向双闸门、text 默认压缩 · 2026-10-23 · accepted

**决定：**
1. **MCP 默认不返回成人向**：用户级设置「允许成人向内容」默认关闭（[§5.9](05-data-models.md#59-mcp-设置) / [§6.9](06-endpoints.md#69-mcp-设置)），且每次调用还要显式 `allowAdult: true`（[§10.3.1](10-mcp.md#1031-内容范围成人向默认关闭)）。
2. **工具 text 默认压缩**：`detail` 默认 `compact`，`structuredContent` 永远完整（[§10.4.6](10-mcp.md#1046-memesummary工具内统一的对外表示)）。
3. **`pick_meme_for_reply` 增加 `inline`**（默认 `true`，IM 机器人传 `false`，省掉缩略图 base64）。
4. **`pick` 增加检索兜底**：原句为空 → 词表关键词重试 → 仍空则安全随机；不再让聊天场景空手而归。

**为什么成人向默认关闭。** 实测库里 362 张有 10 张成人向；Web 端全库可读是产品设计（[§9.1](#91-库是共享的--2026-09-13--accepted)），但 MCP 的输出会直接进群聊、进别人的机器人。默认值决定的是"事故率"，不是"能力上限"——需要的人自己开。

**为什么是两层闸门，而不是只开设置或只传参数。** 只开设置就默认返回，会让一次普通搜索突然混进成人向图；只传参数不看设置，等于令牌能绕过账号意图。两层同时成立才返回；设置关闭时传 `true` **报工具错误**而不是静默忽略——静默会让调用方以为"传了就一定有"。

**为什么是用户级而非令牌级。** v1 只服务本人/自己的圈子；按令牌分会让设置页变成"每个令牌一个开关"，而真实需求（家庭 bot / 私人 bot）还没出现。将来出现再拆，存量令牌默认 `false` 即可平滑升级。

**为什么 text 要压缩。** 实测 `search_memes` 10 条 text **5.9 KB**、`pick` 一次 wire **43 KB**（其中 32 KB 是缩略图 base64）。聊天上下文是稀缺资源；机器人要完整字段可以读 `structuredContent`，不需要把 text 变重。`compact` 只给选图必需的字段（id / 描述 / OCR / 合并标签 / 是否动图 / MIME / URL）。

**为什么 `pick.inline` 可关。** IM 机器人只要 URL；只有聊天客户端需要 `image` content。默认 `true` 保聊天体验，bot 传 `false` 省字节。

**为什么 `pick` 要有兜底。** 实测真实聊天语气（长句）返回 `chosen: null`，短关键词正常——真实的群聊没人按标签说话。先词表关键词重试，再在安全范围内随机挑一张并在 text 里注明；空手比"不完美但有图"更差。

**代价：** 多一张设置表、两个设置端点、工具参数变多、text 契约变化；设置页多一个开关与开启确认；测试面变大。**都是可接受的一次性成本。**

**放弃了什么：**

1. **在 Web 端也隐藏成人向**——那不是这次要改的产品语义；MCP 的默认值单独收口。
2. **按令牌配置内容范围**——v1 不做，理由见上。
3. **返回相似度分数**——与 [§9.34](#934-人物整图向量自动成组人来命名与合并系列是人工维护的父级--2026-09-29--proposed) 同一条：数值外露会长出第二套阈值。
4. **MCP 会话记忆（"别重复发同一张"）**——保持无状态；如需要，用显式的 `excludeMemeIds` 参数（另立契约），不做服务端会话。

**什么情况下推翻：**

1. 出现"默认关闭导致正常使用受阻"的真实反馈 → 重新评估默认值（但"默认开启"需要产品负责人明确同意）。
2. 机器人需要按渠道/人群给出不同策略 → 升级为令牌级或 `channel` 级。
3. 评测集显示 compact 丢掉了选图必需的信息 → 调整 compact 字段，而不是回退成 full。
4. 用户明确要求默认允许成人向 → 改默认值并在这里记录风险与范围。

## §9.37 MCP 过滤器：用户级排除式标签过滤 · 2026-10-23 · accepted

**决定：** MCP 增加**用户级、排除式**的标签过滤器。用户在设置页「MCP 接入 → 过滤器」按七个词表维度选标签；**一张图只要命中任一维度里的任一选中值，就不会出现在 MCP 结果里**。过滤器对 `search_memes` / `pick_meme_for_reply` / `random_meme` / `get_meme_image` 全部生效，`list_vocab` 仍是全量词表；不影响 Web 端。成人向不允许进入过滤器，由 [§9.36](#936-mcp-内容范围与上下文成本成人向双闸门text-默认压缩--2026-10-23--accepted) 的内容范围单独控制。

**为什么是排除，不是"只包含"白名单。** 多选白名单绕不开 ALL/ANY 的语义选择（选「猫」「狗」是任意一个还是两个都要？），而两种解释都会改变检索含义；排除式的「命中任一即排除」没有歧义。需要按人群做白名单时，应该在令牌/渠道层另立模型。

**为什么是用户级，不是每令牌。** v1 的用户就是本人/自己的圈子；设置页当前只有一个「MCP 接入」入口，把过滤器放到每个令牌里会让入口分裂。需要"家庭 bot / 私人 bot 不同策略"时再升级。

**为什么四个工具都生效，而不是只过滤搜索结果。** 过滤器的目的是"MCP 不返回这些内容"。只过滤 search/pick 而 `get_meme_image` 仍可按 id 取，等于留了一个绕过口；`random_meme` 不过滤也会随机漏出。`list_vocab` 不隐藏词条：它描述的是词表全集，模型用被排除的词检索自然会得到空结果。

**为什么不把过滤器做成工具参数。** 它是账号设置，不是调用方每次的选择；做成参数意味着调用方（包括不可信的 LLM）可以自行放宽范围。工具只被动应用账号设置。

**代价：** `user_mcp_settings` 多一个 JSONB 列；检索/随机/单条都要过滤并多取候选；缓存 key 必须包含过滤器；设置页多一个入口和一个选择器 Sheet；测试面增加。**都是可接受的一次性成本。**

**放弃了什么：**

1. **只包含（白名单）**——语义歧义，见上。
2. **把成人向放进过滤器**——两套内容控制会互相打架；成人向继续只由内容范围控制。
3. **每令牌过滤器**——v1 不做，入口保持单一。
4. **在 Web 端同时应用**——过滤器是 MCP 的账号设置，不是 Web 的浏览偏好；Web 继续全库可读。

**什么情况下推翻：**

1. 出现按令牌/渠道定制内容范围的真实需求 → 升级为令牌级或 `channel` 级。
2. 用户明确要白名单且能接受 ALL/ANY 规则 → 另立字段与契约，不改造现有排除语义。
3. 过滤器导致检索结果过少（大面积排除常见标签）→ 在 UI 增加影响提示，而不是放宽过滤。
4. 性能实测不合格（多取候选 + 过滤）→ 把过滤下沉到数据层共享 SQL，但要先证明 Web 与 MCP 的过滤语义可以共用。

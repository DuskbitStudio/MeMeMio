## 1. 为什么要做

托管型 MCP 宿主（`claude.ai` connectors、ChatGPT 的自定义 connector）**没有填写自定义请求头的地方**。它们只会做一件事：被 401 之后读 `resource_metadata`，自己去找授权服务器、动态注册、跳授权页、换令牌。今天这些宿主接不上本服务，只能靠原生客户端或 `mcp-remote` 桥——而那恰恰是需要「分享给不写代码的人」的场景。

改动是把 `/mcp` 从「只认 PAT」变成「认 PAT 或 OAuth 访问令牌」，**不是替换**。现有令牌与现有客户端一个字都不用改，唯一可观察的差异是 401 多一个 `resource_metadata` 参数——按 RFC 6750，不认识的参数必须忽略。

**为什么和 api 同进程、而不是单独一个授权服务**：授权服务器要读写同一张 `users`、同一份 `user_mcp_settings`（成人向与过滤器），还要在同意页上认 cookie 会话。拆出去就得跨进程共享会话与设置，换来的只是两个部署单元。同源还让 `resource` 与 `issuer` 天然一致（[§9.38](../spec/09-decisions.md)）。

## 2. 做完的标准

**发现与注册**

- `GET /.well-known/oauth-protected-resource` 与 `GET /.well-known/oauth-protected-resource/mcp` **两份都返回**同一份 JSON，`resource` 逐字等于 `<origin>/mcp`（RFC 9728 的两种形态都试）。
- `GET /.well-known/oauth-authorization-server` 返回 RFC 8414 文档，`code_challenge_methods_supported` 含 `S256`，`authorization_response_iss_parameter_supported: true`。
- 三份文档带 `Access-Control-Allow-Origin: *`；`/mcp` 仍然对任何 `Origin` 回 403，例外只在这三份上。
- `POST /oauth/register` 发 `mmc_` 开头的 `client_id`，**不下发 `client_secret`**；`redirect_uri` 含 `fragment`、非 https 且非 localhost、超过 10 个，都整项拒绝。

**授权流程**

- 完整走通一次：`/oauth/authorize` → 未登录跳 `/login?next=…` → 同意页 → 允许 → 302 回 `redirect_uri` 带 `code` / 原样 `state` / `iss` → `POST /oauth/token` → 拿到的令牌能调 `tools/list`。
- `client_id` 或 `redirect_uri` 不合法时**不重定向**，回 400 JSON（防开放重定向）；其它错误 302 回去带 `error`。
- `code_verifier` 不对、`redirect_uri` 与发码时不一致、码重放：都是 `400 invalid_grant`；**码重放同时撤销该 grant**。
- 同意页提交必须走 cookie 会话；带 Bearer 提交返回 `UNAUTHENTICATED`（反之 `/mcp` 不认 cookie，这条原有行为不许动）。

**令牌生命周期**

- 访问令牌 1 小时，形状仍是 `mcp_` + 43 字符，`/mcp` 上与 PAT 走同一条校验路径。
- 刷新令牌 `mmr_`，30 天滑动、单次使用、用后旋转；**旧刷新令牌再次出现即视为泄漏，撤销整个 grant 并让在用的访问令牌立刻 401**。
- 「已连接应用」撤销后下一次 MCP 请求 401；撤销是幂等的，重复删同一个 id 仍返回成功语义（见 §6.10 的错误码表）。
- 同一用户最多 20 个活跃 grant；第 21 个在同意页提交时返回 `VALIDATION_FAILED`（`details.fields.grantLimit`）。

**不回归**

- PAT 创建、列表、撤销、限流、`last_used_at` 节流全部不变；「每人 10 个」的计数**只数 `kind='pat'`**——授权 20 个也不挤掉 PAT 名额。
- 软删的图仍然不出现在工具结果里；OAuth 令牌读到的范围与 PAT 完全相同（含 `user_mcp_settings` 的成人向与过滤器）。
- 新表全部进 `api/tests/helpers/test-db.ts` 的 truncate 清单，否则测试之间会互相污染。

## 5. 两端共用的边界

- **写路径、软删、Key 不出响应**三条硬边界不受影响：OAuth 令牌只读，所有工具读路径原本就带 `deleted_at is null`，签发的令牌任何接口都不回显。
- **同意与管理只认 cookie**：`/api/v1/oauth/*` 不接受 Bearer；`/mcp` 不接受 cookie。两条反向规则都要有测试，不是靠注释。
- **类型不等于语义**：Hono RPC 能推出 `{ clientName, clientId, redirectHost, scope, expiresAt }` 的形状，推不出「撤销后立刻 401」和「码重放要撤 grant」——这两条只靠测试。

> 是 **15 条**，旧 0014 已经跑过。原地重生成会让这个库在已有的表上报错；更糟的是手工对齐记账之后，
> 启动检查只比条数，15 对 15 照样通过，留下一张缺列的表。
>
> **实际发生的**：总管给的是 bash 写法，PowerShell 的 `rm` 不接受空格分隔的多个路径，删除没执行，0014 保住了；
> 随后 `db:generate` 拿 0014 快照比对 `schema.ts`，生成了增量的 `0015`——正好是规则要求的「写下一个迁移改回来」。
>
> **0015 已核实**：SQL 只有一句 `ALTER TABLE "oauth_grants" ADD COLUMN "redirect_uri" text NOT NULL;`；
> `0015_snapshot.json` 的 `prevId` 等于 0014 的 `id`，两份快照除 `oauth_grants.redirect_uri` 外**完全相同**，没夹带别的漂移。
> 那次 `diff` 在 PowerShell 里是 `Compare-Object` 的别名，比的是两个路径字符串、不是文件内容，**不算证据**；
> 证据是上面的快照比对。
>
> **`NOT NULL` 没有默认值**：对空表没问题（0014 没进过 git、没部署过；测试库刚由 0000 重建）；开发库的 `oauth_grants` 如果已有行，
> 迁移会失败。drizzle 把全部待跑迁移放在**同一个事务**里（`drizzle-orm/pg-core/dialect.js` 的 `session.transaction`），
> 失败整体回滚，不会只跑一半。
>

## 9. 已知取舍与后续

- **只支持公户端 + DCR，不做机密客户端**：v1 没有「给某个内网服务手工登记 client」的入口。真有需求再开，不在这一轮顺手加。
- **CIMD 不做**：服务端主动抓客户端给的 URL 是 SSRF 面（[§10.9](../spec/10-mcp.md#109-明确不做)）。只支持 CIMD 的客户端这一轮连不上。
- **同意页一律标「未验证」**：DCR 无法核实应用身份，界面不假装能核实。
- **不做按应用区分权限**：只有 `mememio:read` 一个作用域，与 PAT 等价。将来要加写权限，先过 [SPEC §8](../spec/08-collaboration.md)。

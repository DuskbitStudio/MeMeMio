# 页面地图：把「动作在哪出现」定成规则

**状态**：`planning`——**要先裁定才能动手**（§3 剩一处，是跨端的裁定 3；原四处里的 1、2 已由[检索与筛选合流](../_archive/joint-tasks/2026-09-26-检索筛选合一.md)裁定，4 已由[设置页分区导航](../_archive/joint-tasks/2026-10-25-设置页分区导航.md)裁定）
**性质**：以 web 单端为主。产出是**文档**：地图本体归 `web/agents/rules/`，取舍理由归
[SPEC §9](../spec/09-decisions.md)；**裁定 3 一动就是跨端契约，要 SPEC 先行**。

## 1. 为什么要做

2026-09-25 的问题是「是否应该重新考虑，捋清楚前端页面的布局与交互」。走查已经把现状看清了
（[四页走查](../_archive/joint-tasks/2026-09-25-web-page-walkthrough.md)），撞出来 6 条，其中
**四条不是缺陷，是「没有那条规则」的症状**：

| 症状 | 缺的是哪条规则 |
|---|---|
| 全屏阅览整屏没有发送入口，只有 `Ctrl+C` 而界面没提 | 「发送」在哪些面出现、以什么形式 |
| 管理动作只长在浏览页，搜到标错的图要换种筛法再找 | 「管理动作」在哪些面出现 |
| 管理员与成员共用「设置」入口，成员不被告知差异 | 管理员分段的**可见性规则** |
| 重建索引 / 重新打标与配置同一条滚动轴（整页 3262px） | 「配置」与「运维动作」在页面上怎么分 |

它们各自都能单独打个补丁——**那正是 09-21 到 09-24 逐页迁移的老路**：每页都对、补完还是没人回答
「同一个动作该在哪出现」。这次要补的是那个答案本身。

**为什么是文档任务而不是改代码任务**：地图先立起来，之后每一次「这个按钮放哪」才有依据；
反过来先改，等于又攒一批只活在注释里的决定。

## 2. 已经查明的事实

下面每条都是 2026-09-25 走查**实测**的，不是读代码推测的（现场与截图见
[四页走查](../_archive/joint-tasks/2026-09-25-web-page-walkthrough.md)的「web 端验收」）：

- 现在有六条路由：`/`（搜索 + 随机图墙）、`/browse`、`/import`、`/settings`、`/login`、`/register`，
  外加开发期才有的 `/ui`。`/admin/*` 是三条重定向。
- 「发送」**两套可见 + 一套不可见**：搜索卡片的常驻按钮、浏览页「⋯」菜单里那一项（同一个 `sendMeme`）；
  全屏阅览里没有入口，只有 `Ctrl+C`，界面上一个字没提。
- 管理动作（`MemeActions` / `MemeEditPanel`）**只有浏览页有**；搜索结果卡片没有动作槽；
  阅览器里没有编辑、删除，也没有收藏。**搜到一张标错的图得换一种筛法再找一遍。**
- **一张图没有自己的地址**：开/关阅览器、翻页，`location.href` 与 `history.length` 都不变。
  分享粒度是「一次搜索」（顺序可复现），随机图墙刻意不进 URL。
- 顶栏 56px，常驻内容只有折叠按钮（导入时多一个「导入 n/m」）；登出在侧栏底部，
  900px 视口里距顶 856px。
- 成员看到的是**只有一段、且不解释为什么别人的更长**的设置页。

### 裁定 3：单张图要不要有自己的地址 —— ⚠️ **跨端**

**现状**：全仓没有一处 `pushState` / `replaceState`。开 / 关阅览器、翻页都不进 URL、不产生历史；
把同一串地址重开，阅览器是关着的。分享粒度是「一次搜索」而不是「一张图」。

| 选项 | 代价 |
|---|---|
| **A** 给 `/meme/{id}` | 引入「单张图」这个路由形态；`/import` 的待确认卡片、将来任何零散入口都要有对应行为 |
| **B** 只把阅览器当前那一张写进 query（`?at=3`），刷新 / 分享回到同一屏同一张 | 不动路由形态，但阅览器状态进 URL 的规则要立起来（翻页就改地址、要不要进历史） |
| **C** 维持现状 | 「指向一张图」这件事做不到；但目前也没人真的需要过 |

**倾向**：**先不动，但把它作为一条 SPEC 决策记下来。** 关键不是选哪个——是「没有地址」这件事
**从来没人做过决定**，它是逐页迁移的副产物。记下来之后，下次有人问「能不能发一张图给我」时，
翻开就知道这是选过的，而不是漏的。

**这条一动就是跨端**：URL 形态、`SPEC §6` 的接口、`SPEC §9` 的决策，按
[SPEC §8](../spec/08-collaboration.md) 契约先行。**没裁定之前不要写这段代码。**

### 裁定 4：管理员入口分层与设置页分区 —— ✅ 2026-10-25 已裁定

> **结论**：产品负责人选了下表之外的一条——**设置页仍是一个路由，左侧分区导航（「我的」「全站管理」两组），右侧一次只显示一段**，分区地址沿用 `#锚点`。它取 A 的「一个路由、分组、各有锚点」，又解决了 A 留下的「管理员页仍然长」。实施、分区表与理由见[设置页分区导航](../_archive/joint-tasks/2026-10-25-设置页分区导航.md)，不在这里重复。下表留作当时的选项记录。地图落地时，设置页那一格按那份任务的分区表写。

**现状**：管理员与成员共用同一个「设置」入口；成员看到的是只有一段、且不解释为什么别人的更长的页；
重建索引 / 重新打标两张卡 `id` 为 null、不进锚点目录，却和配置在同一条滚动轴上（整页 3262px）。

| 选项 | 代价 |
|---|---|
| **A** 设置页内分区：配置一组、运维一组，各给标题与锚点，仍是一个路由 | 顺着 [settings-merge](../_archive/joint-tasks/2026-09-18-settings-merge.md) 那次「合并的是呈现不是权限」走；管理员页仍然长 |
| **B** 运维动作面板挪出设置页，另给一个只有管理员能进的区 | 把刚并掉的东西再拆开，与那次裁定反向 |
| **C** 现状不动，只补一句给成员看的说明 | 成本最低；3262px 与「不解释」两条都留着 |

**倾向 A**。牵动的两处：`settings-ux.md §2` 的分段表、以及 `SPEC §9.9` 里成员侧那句契约文案
（**契约文案不能顺手改**，改要走裁定）。

## 4. 做完的标准

1. **地图落在 `web/agents/rules/`**：扩 [`state-navigation.md §4`](../web/agents/rules/state-navigation.md)
   那张路由表，还是另开一份，由执行者按 [documentation.md](../agents/rules/documentation.md) 判
   （判据是「这份东西是导航规则的一部分，还是独立的一类」）。新开的话要登记进
   [`web/agents/rules/INDEX.md`](../web/agents/rules/INDEX.md)。
2. 地图要回答三件事，**每页都要有**：这一页承担什么、用户在这一页能做什么、**每个动作在哪些面出现**。
   写完之后，「这个按钮该放哪」应当能直接查表，不再靠回忆。
3. **每一条都要能在浏览器里指出来**，不写理想态。写「阅览器里可以发送」这种句子之前先确认它已经成立，
   没成立的写成「计划」并标明。
4. **取舍理由进 [SPEC §9](../spec/09-decisions.md)**：地图本体是「现在是什么样」，理由是「为什么是这样」。
   裁定 3 无论选哪个**都必须落一条 §9**（§3 已说明理由）。其余三条只在理由值得长期保留时才落
   ——`documentation.md` 那条「没有选另一条路的理由」是准入门槛。
5. **写完后做一次反查**：§1 那四条症状里，哪些被地图直接消掉、哪些还需要单独改，列成一张表交回来。
6. `node scripts/check-doc-links.mjs` 通过。
